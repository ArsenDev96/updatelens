# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Product

UpdateLens is a WordPress plugin that shows what changes when **one** plugin update runs:

1. Capture WordPress state before a plugin update.
2. Let WordPress run the normal plugin update.
3. Capture state afterwards.
4. Calculate a diff.
5. Show a report in wp-admin.

Initial snapshot sources:

- `wp_options` incl. autoload size / autoloaded options — implemented (`Snapshot\OptionsSnapshotProvider`)
- WP-Cron events — implemented and observed in every analysis (`Snapshot\CronSnapshotProvider`, `Diff\CronDiffBuilder`, `Update\CronObservation`), stored in the analyses table and shown in reports next to Options
- Action Scheduler actions — snapshot and diff engine (`Snapshot\ActionSchedulerSnapshotProvider`, `Diff\ActionSchedulerDiffBuilder`) observed in every analysis (`Update\ActionSchedulerObservation`), stored in the analyses table and shown in reports as the third signal

Current state: foundation (admin screen + status REST route), the `wp_options` snapshot and diff engines, the WP-Cron snapshot and diff engines (observed, stored and reported with every analysis), the Action Scheduler snapshot and diff engines (observed, stored and reported with every analysis), the plugin update analysis lifecycle (`Update\PluginUpdateTracker` → `Update\PluginUpdateAnalyzer` → `Storage\AnalysisRepository`, table `{prefix}updatelens_analyses`) and the read-only reports API (`Rest\AnalysesController` → `Report\AnalysisReports` → `Report\AnalysisReadModel`; see `docs/rest-api.md`), the monitoring baseline (`BaselineMonitoringBaseline`, `GET /updatelens/v1/baseline` via `RestBaselineController` → `ReportMonitoringStart`), and the admin UI: first-run screen, Update History and Analysis Report screens on the top-level UpdateLens menu (`admin.php?page=updatelens`, `src/admin/`), with Potential Impact (review rules on the Net result: `Report\PotentialImpact` → `potential_impact` in the report API → a section on the report overview linking to located rows on signal pages), and the Settings screen (`admin.php?page=updatelens-settings`: the site check opt-in, `Rest\SettingsController`).

## Architecture boundaries

- **PHP owns all WordPress integration and business logic.** Snapshots, diffing, update hooks, storage and any rule about what is "significant" live in PHP under `includes/`.
- **React is presentation only.** It renders data returned by PHP REST endpoints. No UpdateLens business rule may exist only in React.
- React talks to PHP only through REST routes in the `updatelens/v1` namespace (`includes/Rest/`), extending `WP_REST_Controller`. Register them from `Core\Plugin::register_rest_routes()`.
- Prefer standard WordPress APIs (`register_rest_route`, `$wpdb`, `dbDelta`, options, transients, `wp_*` functions) over custom framework layers. No ORM.
- `Core\Plugin` is a thin composition root: it wires hooks and delegates. Keep it small.
- Namespace layout (`UpdateLens\`, PSR-4 from `includes/`):
  - `Core/` – bootstrap, activation, deactivation
  - `Admin/` – wp-admin screens, asset loading and the menu count of new reports (`UnreadReports`)
  - `Rest/` – REST controllers
  - `Snapshot/` – capture safe state; `Diff/` – compare snapshots
  - `Update/` – WordPress updater hooks (`PluginUpdateTracker`) and lifecycle rules (`PluginUpdateAnalyzer`, `CronObservation`, `ActionSchedulerObservation`, `UpdateClassifier`)
  - `Storage/` – schema (`Schema`, `dbDelta`), SQL (`AnalysisRepository`), JSON persistence formats (`*Codec`)
  - `Report/` – safe read models of stored analyses for REST (`AnalysisReadModel`) and read access with lifecycle maintenance (`AnalysisReports`); the monitoring start (`MonitoringStart`)
  - `Baseline/` – monitoring baseline: when monitoring started and the plugin inventory then (`PluginInventory` pure, `MonitoringBaseline` option wrapper)
  - `SiteCheck/` – before/after site checks (homepage, REST): classification and comparison, check sessions, the start/report admin-ajax endpoints, the homepage/REST verification markers, BEFORE baselines (`Baselines`, `BaselinePage`) and the updater activity ledger (`UpdateActivity`; see Site check rules); the browser runner is `src/admin/site-check/`, loaded by the baseline entry `src/admin/site-check-baseline.ts` and, for AFTER runs, by the update follow-up entry. Baselines are attached to analyses (`Update\SiteCheckObservation`), AFTER runs are bound to them (`Update\SiteCheckAfter`) and compared in the report (`Report\SiteCheckReport`, `site_checks`) and evaluated by Potential Impact (`potential_impact.site_checks`, shown in the report overview's Potential Impact section); the opt-in (`Settings`) is saved on the UpdateLens Settings screen
- The admin app is TypeScript + React + Tailwind + shadcn/ui in `src/admin/`, built by Vite into `assets/admin/dist/`. There is no public/frontend app.
- The same Vite build has a second entry, `src/admin/update-follow-up.ts` (no React, no UI, no strings): `Admin\AdminAssets::enqueue_update_follow_up()` loads it only where core's `updates` script is enqueued, for users with `update_plugins`. It posts the `updatelens_settle` admin-ajax action (see Update lifecycle invariants), because REST requests never fire `admin_init`, where plugins run upgrade routines. With site checks enabled it also gets the site check nonce (`siteChecks`) and runs the AFTER checks of the analyses that request settled (`update-follow-up/afterChecks.ts`, see Site check rules).
- A third entry, `src/admin/site-check-baseline.ts` (no React, no UI, no strings), collects site check BEFORE baselines: `Admin\AdminAssets::enqueue_site_check_baseline()` loads it only where `SiteCheck\BaselinePage::settings()` allows (see Site check rules). It posts the site check admin-ajax actions.

## WordPress.org compatibility

The plugin must stay distributable on WordPress.org:

- GPL-2.0-or-later compatible code and dependencies only.
- Minimums: PHP 7.4, WordPress 6.2 (`%i` placeholders and `WP_HTML_Tag_Processor` need 6.2). Don't use newer APIs without a guard or a deliberate minimum bump in `updatelens.php`, `readme.txt` and `phpcs.xml.dist`.
- Stay clean on the newest PHP too: explicit nullable types (`?callable $now = null`, never `callable $now = null`, deprecated since PHP 8.4 and reported whenever the class loads).
- Prefix all globals (`updatelens_` / `UPDATELENS_` / `UpdateLens\`). Text domain is `updatelens`.
- Translate user-facing strings: PHP via `__()`/`esc_html__()` etc.; JS via `__()` from `@wordpress/i18n` (mapped to `wp.i18n`).
- Don't bundle WordPress-provided packages. Any `@wordpress/*` import must be added to `WP_GLOBALS` in `vite.config.ts` **and** to the script dependencies in `Admin\AdminAssets::DEPENDENCIES`.
- No obfuscated code; `src/` ships in the release ZIP. The build keeps `translators:` comments (Babel + Terser instead of esbuild in `vite.config.ts`), because translate.wordpress.org extracts JS strings from the built bundle; same string, same translator comment.
- **The release runtime is production-only.** `AdminAdminAssets` (UpdateLens's own code) enqueues the build from `assets/admin/dist/manifest.json`: no dev-server discovery, other origins or loader filters. The Vite dev-server helper is the must-use plugin `dev/updatelens-vite-dev-server.php`, which is never shipped. No heredoc/nowdoc (Plugin Check error).
- Ship every third-party notice: list distributed third-party code in `THIRD-PARTY-NOTICES.txt`.
- Keep Plugin Check (run natively, never in Playground) at zero errors and warnings: SQL is written out as literal `prepare()` templates; only values and identifiers are placeholders.

## Security and privacy rules

- Admin screens and REST routes require `Core\Plugin::CAPABILITY` (`manage_options`). Every REST route needs a real `permission_callback` — never `__return_true`.
- Sanitize and validate all input (REST `args` with `sanitize_callback`/`validate_callback`, `sanitize_*`, `absint`, …).
- Escape all server-rendered output (`esc_html`, `esc_attr`, `esc_url`, `wp_kses_post`).
- Use nonces for state-changing requests. REST calls from the admin app go through `wp.apiFetch`, which sends the `wp_rest` nonce.
- Use `$wpdb->prepare()` for every custom SQL query with variable input.
- Never expose or persist sensitive `wp_options` values unnecessarily (credentials, keys, tokens, salts, session data). Snapshot code must minimise and/or mask values; reports should show what changed without leaking secrets.
- **No telemetry.** No external HTTP requests or data transmission. No external SaaS/backend in V1.

## Snapshot invariants

- **Raw `option_value` strings never leave `Snapshot\OptionsSnapshotBuilder`.** They are never persisted, logged, returned from REST or held in snapshot objects. Snapshots keep only name, keyed fingerprint, byte size and autoload state; tests assert a fake secret appears in no serialized form.
- **Option values are compared by fingerprint**: HMAC-SHA256 (`Snapshot\OptionValueHasher`) keyed from `wp_salt( 'auth' )`. Never use an unkeyed hash. Fingerprints are only comparable within one site and one set of salts. Don't expose fingerprints via REST unless a task asks for it.
- Every fingerprint domain derives its own key through `Snapshot\KeyedHasher` with its own label (`updatelens:option-value:v1`, `updatelens:cron-args:v1`, `updatelens:action-scheduler-args:v1`), so identical bytes never fingerprint alike across domains. Never reuse a label for another domain.
- Read the stored strings via `$wpdb` (no `get_option()`, no unserializing); size is `strlen()` bytes. Snapshot code is read-only.
- Autoload state: keep the raw column value and normalize via `Snapshot\AutoloadPolicy` (core's `wp_autoload_values_to_autoload()` on 6.6+, `yes` only before). Don't hardcode `yes`/`no`.
- Snapshot content must be deterministic: sorted byte-wise by name, no timestamps inside the compared data.
- **Snapshot sources must not overlap.** Each piece of state belongs to exactly one provider. `wp_options` excludes `cron` because WP-Cron gets its own provider.
- **Noise filtering stays conservative and tested** (`Snapshot\OptionNoiseFilter`): only transients (`_transient_*`, `_site_transient_*`), UpdateLens's own options, `cron`, and the three exact names `wpe_site_transient_update_core|plugins|themes` (persistent copies of update-check records found on WP Engine sites; they appear to be hosting-managed update-check metadata, exact writer unverified). Never a `wpe_` prefix rule: other `wpe_*` options stay. Shipped code assembles these names from `OptionNoiseFilter::HOSTING_UPDATE_CHECK_PREFIX`: Plugin Check's updater check regex-matches `site_transient_update_plugins` (error) and `_site_transient_update_\w+` (warning) anywhere in PHP files, comments included, so never write them out in `includes/` (tests are not shipped). Excluding names changes only new snapshots; stored analyses are never rewritten. Don't exclude persistent options just because they are large or change often (e.g. `rewrite_rules`). Every rule needs a test.
- Every option UpdateLens stores must start with `Core\Plugin::OPTION_PREFIX` (`updatelens_`) so it never shows up in its own snapshots.
- Each snapshot carries a non-secret, versioned fingerprint context (`OptionValueHasher::get_context()`, `hmac-sha256-v1:<hex>`). Bump `OptionValueHasher::SCHEME` whenever fingerprinting changes.

## Diff invariants

- Diffs work only on `OptionsSnapshot` objects; the diff engine never reads the database.
- **Never compare snapshots with different fingerprint contexts** (rotated salts, other scheme): `OptionsDiffBuilder` throws `IncompatibleSnapshotsException` instead of reporting every option as changed.
- **Fingerprints are internal.** The builder compares them; `OptionsDiff` and its records never contain fingerprints, contexts or option values. Tests assert a fake secret appears in no serialized form.
- Raw autoload storage changes (`autoload_value_changed`, e.g. `yes` → `auto-on`) and effective autoload behavior changes (`autoload_behavior_changed`, `is_autoloaded` flipped) are distinct and reported separately.
- Value changes are detected by fingerprint, never inferred from size. An option appears only if value, size, raw autoload or effective autoload differs.
- All deltas are signed `after - before`, in raw bytes/counts. Aggregate deltas come from the two snapshot summaries, not from summing changed records.
- Diff results are deterministic: added/removed/changed sorted byte-wise by name, no timestamps or random ids.

## WP-Cron snapshot and diff invariants

- **Cron is its own snapshot source**, separate from `wp_options` (which keeps excluding `cron`): `Snapshot\CronSnapshotProvider` → `CronSnapshotBuilder` (pure) → `CronSnapshot`; `Diff\CronDiffBuilder` → `CronDiff`.
- **Raw cron arguments never leave `Snapshot\CronSnapshotBuilder`**: never persisted, logged, returned from REST or held in snapshot/diff objects. Only the keyed `args_fingerprint` (`Snapshot\CronArgsHasher`: HMAC of `serialize( $args )`, the canonical form of core's `md5( serialize( $args ) )` event key, so order, keys and types count) is kept. Core's unkeyed md5 key is never stored. Tests assert a fake secret appears in no serialized form.
- **Snapshotting never mutates WP-Cron.** Read with `get_option( 'cron' )`; never `_get_cron_array()` (it rewrites a version-less option) and never any schedule/unschedule/clear function.
- Event records: `hook`, `timestamp` (int), `schedule` (string|null), `interval` (int|null: null for one-time events or when not stored), `is_recurring`, `args_fingerprint`. The `version` marker is not an event.
- **Logical identity = hook + args fingerprint.** Timestamp and recurrence (schedule + interval) are attributes. Several instances per identity are real state (`wp_schedule_event()` has no duplicate check): snapshots keep a sorted list, never a map that could overwrite.
- Matching within one identity, in timestamp order: same timestamp + recurrence → unchanged; same recurrence → **`rescheduled`, never removed + added** (otherwise every normal cron run is noise); other recurrence (`daily` → `hourly`, one-time ↔ recurring, interval) → `changed`; leftovers → added/removed. Different arguments are a different identity → removed + added; never guess they belong together.
- **Malformed cron state fails the whole snapshot** (`Snapshot\MalformedCronStateException`: fixed message, fixed reason code, never data) instead of skipping entries, which would show up as false additions/removals. What core accepts is not malformed: non-array option (= no events), unregistered schedule names, recurring events without interval, empty or numeric hook names. Arrays without the `version` 2 marker are `unsupported_format`. Hook names must be valid UTF-8.
- Deterministic order: snapshots by hook (byte-wise), args fingerprint, timestamp, schedule, interval; diff lists by their array form (hook first). No capture time in snapshots. Different fingerprint contexts → `IncompatibleSnapshotsException`.
- Cron changes are observations, not causes (same wording rules as options); a rescheduled event is often just a normal cron run.

## Action Scheduler snapshot and diff invariants

- **Action Scheduler is its own signal**, separate from `wp_options` and WP-Cron: `Snapshot\ActionSchedulerSnapshotProvider` (WordPress/DB) → `ActionSchedulerSnapshotBuilder` (pure) → `ActionSchedulerSnapshot`; `Diff\ActionSchedulerDiffBuilder` → `ActionSchedulerDiff`. Observed in the lifecycle, stored and reported (see below).
- **A snapshot is the active state only**: `pending` and `in-progress` actions (what Action Scheduler itself treats as existing: `as_has_scheduled_action()`, unique scheduling). Complete, failed and canceled rows are history (often hundreds of thousands, purged by Action Scheduler after 31 days), and logs and claims are operational data: never read them into snapshots or counts. An action that ran, failed or was canceled shows as removed; a recurring run (Action Scheduler stores the next run as a new row) shows as rescheduled.
- **Bounded reads**: only the active rows, in `action_id`-cursor batches (`ActionSchedulerSnapshotProvider::BATCH_SIZE`), never OFFSET, never all rows; rows stream through a generator into the builder. Use Action Scheduler's existing indexes; never add indexes or other schema to third-party tables. Batches are not atomic (like the options snapshot); document rather than lock.
- **Third-party tables are read-only**: only SELECT/SHOW. Never schedule, cancel, claim or run actions, call Action Scheduler's store or query API, initialize or migrate its schema, or call `ActionScheduler_Store::instance()` before `ActionScheduler::is_initialized()`.
- **Unavailable is not empty**: the provider throws `ActionSchedulerUnavailableException` (`not_installed`, `not_initialized`, `unsupported_store`, `unsupported_schema`, `read_failed`) instead of returning an empty snapshot. Supported stores: exactly `ActionScheduler_DBStore`, and `ActionScheduler_HybridStore` only while no `scheduled-action` post is pending/in-progress (Action Scheduler switches to it after a fresh install and after any plugin deactivation). Custom stores and subclasses are unsupported, never guessed. Supported tables: Action Scheduler 3.1.6–4.2.0 (schema 3–9), checked by the columns read.
- **Malformed active rows fail the whole snapshot** (`MalformedActionSchedulerStateException`: `invalid_action`, `invalid_args`, `invalid_schedule`, `unsupported_schedule`; fixed messages, never data) — distinct from unavailability. Never skip rows.
- **Raw arguments never leave `ActionSchedulerSnapshotBuilder`**: never persisted, logged, exposed or held in snapshot/diff objects. Only `args_fingerprint` (`Snapshot\ActionSchedulerArgsHasher`, label `updatelens:action-scheduler-args:v1`): an HMAC of the stored JSON text (`extended_args` when set, else `args`), the same text Action Scheduler compares. Diffs contain no fingerprints; no action, claim or group IDs anywhere.
- **Schedules are never instantiated**: `ActionSchedulerScheduleParser` reads the serialized schedule with `unserialize( …, allowed_classes false, max_depth )` under a length limit and normalizes Simple → `single`, Null → `async`, Interval → `interval` (seconds), Cron → `cron` (expression, fields joined by single spaces, cron characters only). Other classes are `unsupported_schedule`. The scheduled time comes from `scheduled_date_gmt`.
- **Logical identity = hook + group slug + args fingerprint** (Action Scheduler's own uniqueness key). Group slugs are developer-defined identifiers like hooks and are kept; no group → `''`. Several instances per identity are real state: sorted lists, never maps. Matching per identity in time order: same time + schedule → unchanged; same schedule → rescheduled; other schedule (type, interval, cron expression) → changed; leftovers → added/removed. Other arguments or group → removed + added. The status is an attribute, not compared (pending → in-progress is execution).
- Observations, not ownership: never attribute actions to a plugin by hook, group or prefix; WooCommerce and Action Scheduler's own jobs stay in the data.

## WP-Cron in the analysis lifecycle

- **Options and WP-Cron are independent analysis signals.** `wp_options` drives the lifecycle and the global status; Cron (`Update\CronObservation`) is captured at the same moments, right after options, and never changes the status, throws, or blocks the update.
- **A Cron failure never invalidates an options analysis.** Capture errors, malformed state, codec errors, incompatible contexts and Cron storage failures only make the affected Cron phases unavailable. Options incompatibility/failure keeps its global behavior.
- **Malformed Cron state disables Cron** for the phases that need that snapshot (`malformed_cron_state`); never skip records instead.
- **Cron phase availability is independent.** during = BEFORE+IMMEDIATE, post = IMMEDIATE+SETTLED, final = BEFORE+SETTLED; a missing snapshot affects only its dependents (malformed IMMEDIATE → during/post unavailable, final still computed). A fingerprint-context mismatch affects only the pair compared.
- `cron_*_reason` holds an `Update\CronPhaseReason` code (fixed codes, never messages). **Every Cron phase of a terminal analysis has exactly one of a diff or a reason**; in an open analysis a phase with neither is pending. The first cause wins: later lifecycle events never overwrite a resolved phase. Ending states map to `update_failed`, `analysis_abandoned`, `analysis_ended` (options failed/incompatible) or `settle_expired`; analyses from before schema 3 are `not_captured`.
- Cron columns are written in the same statement as the options transition. If it fails, it is retried without signal payload, one signal at a time (`PluginUpdateAnalyzer::attempts()`: all → without Action Scheduler → without Cron → without both; each signal's `without_payload()` → `storage_failed` for its own phases only), so neither signal's storage can hold the options analysis back or drop the other signal.
- A failed update captures no IMMEDIATE Cron state; an expired settle window takes no late Cron snapshot.
- **The backend preserves every observed Cron change**, including normal and core rescheduling (e.g. `wp_version_check` moving in the post-update phase): no ignore lists, no ownership filtering. De-emphasis belongs to presentation.
- **Raw Cron arguments are never stored, logged or exposed.** Stored Cron snapshots keep `args_fingerprint` (internal); stored Cron diffs contain no fingerprints. Reports read Cron diffs and reasons, never Cron snapshots; History reads only SQL-computed recorded/has-changes flags of the Cron diff columns, never their content or the reasons.

## Action Scheduler in the analysis lifecycle

- **A third independent signal** (`Update\ActionSchedulerObservation`), captured right after Cron at BEFORE, IMMEDIATE and SETTLED. Same rules as Cron: never changes the global status, throws or blocks the update; failures only affect the phases that need the failing capture. No extra settle request or window.
- **Absence is normal**: no Action Scheduler → every phase absent at both captures, never a failure. **Absence is resolved from both captures of a phase, never the first alone**: a capture that finds no Action Scheduler is kept as `ActionSchedulerObservation::NOT_INSTALLED_MARKER` in its temporary snapshot column (no payload: `without_payload()` keeps it), and `phase()` stores `not_installed_throughout` (absent at both; reported as `not_installed` via `AnalysisReadModel::ACTION_SCHEDULER_REPORTED_AS`), `newly_detected` (readable at the second), the second capture's failure, or `no_longer_detected` (readable first, absent second). A phase whose second capture never happens gets the lifecycle reason. A stored `not_installed` comes only from older analyses (absent at the phase's first capture, second unknown); never rewrite them. Provider reasons stay distinct (`Update\ActionSchedulerPhaseReason::from_unavailable()/from_malformed()`): `not_installed`, `unsupported_store`, `unsupported_schema`, `unsupported_schedule`, `malformed_action_scheduler_state`; `not_initialized` and `read_failed` are `snapshot_unavailable`. Keep the reason set finite (`ActionSchedulerPhaseReason::ALL`).
- **A phase is available only if both of its captures are readable snapshots**; otherwise it gets the reason of the first capture that failed (first cause wins; absence is not a failure, see above). Availability changes (e.g. not installed at BEFORE, available after) never produce invented added/removed diffs. Context mismatch affects only the pair compared (`fingerprint_context_changed`); options incompatibility stays global and unresolved Action Scheduler phases get `analysis_ended`.
- `action_scheduler_*_reason` + diff: every phase of a terminal analysis has exactly one. Endings: `update_failed`, `analysis_abandoned`, `analysis_ended`, `settle_expired` (during diff kept, no late snapshot); analyses from before schema 4 are `not_captured` (open ones resolve the same way, no snapshots are fabricated).
- Persist only via `Storage\ActionSchedulerSnapshotCodec` (temporary; records + context, never arguments, schedules, logs, claims or IDs; the only other value of a snapshot column is the not-installed marker) and `Storage\ActionSchedulerDiffCodec` (no fingerprints or context; counts and deltas validated). Reports read only the Action Scheduler diff and reason columns, History only flags of the diff columns; never the snapshot columns.
- Snapshot diffs cannot see an action that was queued and completed between two captures (it is in neither snapshot).

## Monitoring baseline invariants

- **Never invent old history.** UpdateLens observes from activation on. Updates before it are never reconstructed (no file dates, update transients, changelogs, logs, plugin metadata, Action Scheduler logs or guesses from current state), and no synthetic analyses are created. The UI says earlier updates were not observed.
- The baseline is an inventory marker, not a snapshot: option `updatelens_monitoring_baseline` (not autoloaded), JSON via `StorageMonitoringBaselineCodec` (`schema`, UTC `started_at`, plugins with only `file`, `name`, `version`, `active`). Never settings, option values, arguments, URIs, update/license data or user data. UpdateLens itself is excluded (its updates are not analyzed). Inventory comes from `get_plugins()`/`is_plugin_active()`.
- **Written once, never rewritten**: `MonitoringBaseline::ensure()` adds it (`add_option`) on activation and, as a retry or for upgraded sites, on load of the UpdateLens screen; never on other requests. An existing value, even unreadable, is never replaced; updates, activations and new reports never change it; new plugins are not appended. `ensure()` never throws, so activation never fails because of it. Single site only.
- **Visible start = earlier of baseline time and the first analysis** (`ReportMonitoringStart`). A baseline recorded after existing analyses (sites upgraded from Beta 2) is not shown as the plugins at the start (`plugins: null`). Missing/corrupt baseline → `null` fields (HTTP 200), never an error.
- Deactivation keeps the baseline; `uninstall.php` deletes it.

## Update lifecycle invariants

- **UpdateLens observes the WordPress updater; it never owns it.** No custom updater, and never alter packages, files, activation state, update metadata, credentials or responses. Upgrader filters return their input unchanged.
- **Analysis failure must never block an update.** Hook callbacks catch every `Throwable`; never return a `WP_Error` from an upgrader filter because of UpdateLens.
- **V0.1 attributes single-plugin updates only** (`UpdateClassifier`): `Plugin_Upgrader::upgrade()` or `bulk_upgrade()` with exactly one plugin ("Update now" is a one-plugin `bulk_upgrade`, so `is_multi` cannot tell single from bulk — use `bulk` + `update_count` from `upgrader_pre_download`). Ignored: multi-plugin bulk updates, installs, themes, core, translations, cron/WP-CLI updates, UpdateLens itself, and Multisite (the tracker is not registered there).
- Flow: `upgrader_pre_download` → BEFORE (`captured`); `upgrader_install_package_result` + `upgrader_process_complete` → IMMEDIATE + during-update diff (`awaiting_settle`) or `failed`; the browser's follow-up request (`follow_up`), else `shutdown` of a **later** eligible wp-admin page request (`admin_shutdown`), within the settle window → SETTLED + post-update and final diffs (`completed`). States: `Update\AnalysisStatus`; settle outcomes: `Update\SettleOutcome`.
- **Follow-up request** (`Update\FollowUpRequest`, `PluginUpdateAnalyzer::settle_follow_up()`): after `wp-plugin-update-success`, the follow-up script waits for jQuery's `ajaxComplete` with `wp.updates` idle (not locked, empty queue; core fires the success event before `ajaxAlways` unlocks and starts the next job, WordPress 6.2–7.1), then sends **one** `admin-ajax.php?action=updatelens_settle` POST (`keepalive`, best effort) listing the plugins updated since its last request. No polling, no retries, no UI. The handler checks the nonce (`updatelens_settle`), `update_plugins` and the strict basename list, then settles **only** the open analyses of those plugins started by the **same user**; other pending analyses are left alone. Responses are per-plugin result codes only (`settled`, `not_pending`, `not_ready`, `not_allowed`, `expired`, `capture_failed`, `analysis_failed`, `conflict`, `storage_failed`), never snapshot or diff data. Queued updates are still cut by `next_update`.
- **Page-load settling needs an eligible request** (`Update\SettleEligibility`): wp-admin, logged in, `update_plugins`, `admin_init` already fired; never Ajax (other than the follow-up action), REST, cron, CLI or frontend. Anonymous wp-admin hits are redirected before `admin_init` and must never settle.
- **A request settles an analysis only if it started after IMMEDIATE was taken** (both the follow-up and page loads): the request start must be strictly later than `immediate_captured_at` (schema 5, `decimal(16,6)`, `microtime( true )` written after the IMMEDIATE captures), compared in whole microseconds with the start rounded down (a start within the same recorded microsecond is not later). The request start is WordPress's `$timestart` (`Update\RequestStart`: `timer_start()` in wp-settings.php, `microtime( true )`, before any drop-in, must-use plugin or plugin loads; captured once when `updatelens.php` loads), so both values come from PHP's clock. **Never `REQUEST_TIME_FLOAT`**: it is the web server's clock; Apache on Windows takes it from the coarse system tick (`GetSystemTimeAsFileTime()`, measured up to 14 ms behind `microtime()`), so follow-ups sent ~10 ms after IMMEDIATE read as earlier (`not_ready`; 2 of 50 Chrome updates). Never the time of evaluation either: a request that started before IMMEDIATE stays too early however long it runs. A missing, malformed or future `$timestart` leaves the start unknown: the request settles nothing. Second precision is not enough (follow-ups usually start within the same second); rows without the column (schema < 5) accept only a request that started in a later second than `updated_at`. The next-update cut does not use this rule (it must stop before the next update's changes). The analyzer's clock is `microtime( true )`; its request start comes from `PluginUpdateAnalyzer::create()`.
- **The update request's own shutdown never settles** (the analyzer remembers the analyses it created in this request). A request that activates/deactivates the analysed plugin does not settle it. Concurrent settle attempts are safe: compare-and-set on `status`, so exactly one writes the Net result (the others report `conflict`).
- Before any other update starts, analyses awaiting settle from earlier requests are settled first (or expired, if past their deadline), so another update's changes never appear in their phases. Another update in the same request abandons that request's analysis.
- **BEFORE and IMMEDIATE snapshots are temporary** (`options_*_snapshot`, `cron_*_snapshot`, `action_scheduler_*_snapshot`): cleared on every final state, in the same write. Final records keep metadata, status/error, settle outcome, the phase diffs and Cron/Action Scheduler phase reasons — never option values, Cron or Action Scheduler arguments, fingerprints or snapshots.
- Columns are prefixed by signal (`options_*`, `cron_*`, `action_scheduler_*`, `site_check_*`); the generic v1/v2 names are renamed by `Schema::RENAMES`.
- **Site check BEFORE columns** (schema 6, `site_check_<home|rest>_before` + `_before_reason`): written once in the analysis INSERT (`PluginUpdateAnalyzer::begin()` via `Update\SiteCheckObservation::before()`, with `site_check_update_started_at`, schema 7: the update's ledger time with microseconds), never changed afterwards and kept on every final state (failed, abandoned, expired); not temporary snapshots. Older rows are never rewritten: both NULL reads as `not_captured`.
- **Site check AFTER columns** (schema 7, `site_check_after_started_at`, `site_check_<home|rest>_after` + `_after_reason`): written only after the analysis completed, by guarded single-row UPDATEs (`AnalysisRepository::claim_site_check_after()`: `IS NULL` + owner + `completed` + `follow_up`; `record_site_check_after()`: both columns of the check `IS NULL`, claimed, owner), each at most once; never by `transition()`, so the completed analysis and its Net result are never touched. Older rows are never rewritten: a NULL update start reads as AFTER `not_captured`.
- **Every updater download records itself first** (`PluginUpdateTracker::on_pre_download()`, any upgrader incl. themes, core, translations, multi-plugin bulk, cron and WP-CLI; WP_Error short-circuits excluded) in the site-wide `SiteCheck\UpdateActivity` ledger, and ends at that request's `shutdown`; the analysis receives that record (`update_starting( …, $activity )`).
- **The follow-up response names what it settled**: `settle_follow_up( …, &$settled )` returns plugin => analysis ID for each analysis this request settled; the response adds `analysis` and `site_checks` (whether its AFTER checks should start, `SiteCheckAfter::wanted()`) to those entries only, never "the latest analysis of the plugin".
- Persist snapshots/diffs only as versioned JSON via `Storage\*Codec` (never PHP `serialize()`); decoding validates everything. Stored errors use fixed messages and sanitized codes — never WordPress error messages (paths, URLs).
- Every non-final analysis has a non-NULL `active_plugin` (unique), so there is at most one open analysis per plugin while history is kept. Transitions are compare-and-set on `status`.
- Timestamps are UTC (`gmdate()`). Stale `captured` analyses (> `PluginUpdateAnalyzer::STALE_AFTER_SECONDS`) are abandoned on a later admin page request; no cron.
- Bump `Storage\Schema::VERSION` when the table changes; `Schema::maybe_upgrade()` runs `dbDelta()` on bootstrap only when the stored version differs. dbDelta cannot rename: renames run before it (`Schema::install()`).
- A table missing despite a current version is recreated by `Schema::repair()`, which runs only in bounded contexts (the UpdateLens screen and report REST reads), never on every request.

## Observation and attribution rules

- **UpdateLens reports observed changes, not guaranteed causality.** Names and labels describe _when_ a change was observed, never that the plugin caused it (no `plugin_changes`, `caused_by`, …).
- Phases are distinct and all kept (`Update\ObservationPhase`): `during_update` = BEFORE → IMMEDIATE (inside the update request; strongest association); `post_update` = IMMEDIATE → SETTLED (the follow-up request or the first eligible admin request after it; other site activity may contribute; one observation, not proof that migrations or background work finished); `final` = BEFORE → SETTLED (net).
- **The settle window is bounded**: `PluginUpdateAnalyzer::SETTLE_WINDOW_SECONDS` (300, inclusive) from the persisted `settle_deadline`. After it, the analysis completes with `settle_outcome = expired`: no late settled snapshot, post-update and final diffs stay NULL. Late settling must never collect unrelated site changes indefinitely.
- `settle_outcome` explains every NULL phase diff: `admin_shutdown`, `follow_up`, `next_update`, `expired`, or `not_applicable` (ended before settling).
- Any incompatible comparison in any phase → `incompatible`; never store partial phase diffs.
- Don't hide core/system options (e.g. `theme_mods_*`, `recently_activated`) from the stored diffs; classification belongs to presentation.

## Reports API rules

- **REST reports expose safe read models, never database rows.** Controllers call `Report\AnalysisReports`; only `Report\AnalysisReadModel` turns rows into API arrays, by whitelisting fields. Controllers never write SQL.
- **Snapshot and fingerprint internals are never API fields**: no snapshots, fingerprints, fingerprint contexts, option values, raw diff JSON, user data or stored error messages. Errors expose a sanitized `code` only.
- **Stored diffs are decoded only through `Storage\OptionsDiffCodec::decode()` / `Storage\CronDiffCodec::decode()` / `Storage\ActionSchedulerDiffCodec::decode()`**, which validates everything; never `json_decode()` stored data elsewhere. An unreadable diff becomes an unavailable phase (`data_corrupt`), never an error with the stored data.
- **Report reads expire overdue analyses first** (`PluginUpdateAnalyzer::expire_overdue()`, same inclusive deadline rule, no late snapshot). Apart from that and `Schema::repair()`, report endpoints are read-only.
- **Reports are provider-aware**: `phases.<phase>.options`, `phases.<phase>.cron` and `phases.<phase>.action_scheduler`, each with its own `available`/`reason`. Never couple one signal's availability to another's; a phase is unavailable only if all are. Adding a signal is additive: existing signal objects never change. **Provider corruption stays isolated**: an unreadable stored diff makes only that signal's phase `data_corrupt`; the report is still HTTP 200.
- Cron REST output is only `CronDiffCodec::decode()` output (hooks, timestamps, schedules, intervals, flags, counts). **Never Cron arguments, args fingerprints, md5 event keys, the Cron fingerprint context, snapshots or raw JSON.** Stored Cron reasons are whitelisted (`AnalysisReadModel::CRON_REASONS`), anything else is `unknown`; Cron phases without data are explained from the status (`update_in_progress`, `awaiting_settle`) or `not_recorded`.
- **Action Scheduler is the third independent report signal**, read like Cron (`AnalysisReadModel::signal_phase()`): REST output is only `ActionSchedulerDiffCodec::decode()` output (hooks, groups, statuses, timestamps, normalized schedules, flags, counts). **Never arguments, args fingerprints, the fingerprint context, action/claim/group IDs, serialized schedules, logs, snapshots or raw JSON.** Stored reasons are whitelisted (`AnalysisReadModel::ACTION_SCHEDULER_REASONS` = `ActionSchedulerPhaseReason::ALL`), anything else is `unknown`. Pre-schema-4 analyses are `not_captured`, never a zero-change diff.
- History lists read metadata plus per-phase, per-signal flags computed in SQL (the literal query in `AnalysisRepository::find_page()`, in `HISTORY_DIFFS` order): `IS NOT NULL` (recorded) and `NOT LIKE` the codec's escaped `EMPTY_PREFIX` passed as a placeholder (has changes), ordered by primary key. Diff JSON is never selected or decoded for the history; full diffs are decoded only for a single report. If a codec's encoding changes, its `EMPTY_PREFIX` must change with it (codec tests pin both).
- The API exposes facts (`recorded`, `has_changes`), never wording like "4 changes" or "No changes"; presentation belongs in React.
- **Observation-window wording comes from the API** (`observation_window_seconds`); presentation never hard-codes the window length.
- **API timestamps are UTC ISO 8601** (`2026-10-05T17:46:23Z`) or `null`; never convert to site-local time in PHP. Counts, sizes and deltas are JSON integers; flags are booleans.
- Unknown stored statuses/outcomes become `unknown`; never reinterpret them. Unavailable phases always carry a `Report\UnavailableReason` code.
- Post-update observations keep non-causal wording in the API, docs and UI (association `observed_after_update`, never "caused by").
- Database errors never reach REST responses: reads fail with the generic `updatelens_reports_unavailable` (500).
- **`site_checks` is additive and computed on every read** (`Report\SiteCheckReport::build()` inside `AnalysisReadModel::report()`, clock injectable): per check `state` (CheckComparator states, `pending`), `reason`, the `before`/`after` sides (`available`, `reason`, UTC times, the result's verdict and attempt facts, `age_seconds`/`delay_seconds`) and an overall `status` (`pending`, `complete`, `partial`, `unavailable`). Never fingerprints, users, generations, URLs, markers or bodies. Not part of any phase; Potential Impact evaluates it separately (`potential_impact.site_checks`, see Potential Impact rules). Not in History.

## Site check rules (the opt-in and its Settings screen, BEFORE baselines, AFTER runs, the `site_checks` report field and its Potential Impact evaluation)

- **Two fixed checks** (`SiteCheck\CheckDefinition`): `home` (anonymous homepage) and `rest` (`users/me?_fields=id` as the session user). The authentication context is fixed per check. Bump a definition's version whenever its request or classification changes; results of other versions are never compared.
- **Two dimensions stay separate** (`SiteCheck\Attempt`): what the browser observed (`outcome`, `status`, `duration_ms`, `end_marker` / `body`) and whether WordPress was verified as the origin (`origin`: `verified` only when this session's marker came back; `unverified`; `unknown` when nothing was readable). An HTTP 200 alone never passes; a 5xx is an observed HTTP failure whatever the origin, never a claim about who produced it.
- **Classification lives in `ResponseClassifier`**: never pass without a verified origin; missing or stale markers, challenges, unverified 401/403/other 4xx, 429, 503 with Retry-After and network errors are `inconclusive`. A failure or redirect counts only when both attempts agree; a single one is `inconclusive` (`unconfirmed`).
- **Comparison is conservative and per check** (`CheckComparator`, states and reasons in `ComparisonState`): only `newly_failing` (verified pass before, confirmed failure after) is a potential failure finding. Requirements are checked in a fixed order (queued/overlapping update, both results present, definition version, target, user, WordPress login session (the auth cookie's session token, shared by every tab of that login; not a tab identifier), baseline finished before the update and ≤ 600 s old, AFTER started after the update ended, both conclusive). A missing result is `not_run`, never a pass or "no problems"; one check never affects the other.
- **Browser reports are untrusted and bounded** (`ReportValidator`): ≤ 2 KB, exact keys per kind and check, fixed enums; markers are compared in the browser, so no marker, token, nonce, cookie, header value, URL, body or error message is sent or kept. The REST user ID is compared, never kept; unknown REST error codes become `other`. Errors carry fixed reason codes only.
- **No raw URLs or session tokens**: targets and login sessions are keyed fingerprints (`ContextHasher`, labels `updatelens:site-check-target:v1`, `updatelens:site-check-session:v1`). `Storage\SiteCheckResultCodec` stores only facts (verdicts and origin are derived on decode); comparison output (`CheckComparison::to_array()`) has no fingerprints, users or timestamps.
- **Opt-in, signed-in, single site** (`SiteCheck\Settings`, `AjaxEndpoints`): off unless the option `updatelens_site_checks` is `enabled` and the `updatelens_site_checks_enabled` filter does not return false (`Settings::is_enabled()`; every start, report, update screen and update request reads it). Only `wp_ajax_` actions (`updatelens_site_check_start`, `updatelens_site_check_report`), never `nopriv`; each needs the `updatelens_site_check` nonce, `update_plugins`, the opt-in and a login session. Fixed error codes and statuses (`AjaxEndpoints::STATUS`); every response is `no-store, private`. Check URLs come from `AjaxEndpoints::target_urls()` (`home_url()`/`rest_url()`), never from the request. BEFORE baselines start automatically on the update screens; AFTER runs start only from the updating browser's follow-up response (below).
- **The opt-in is saved only by an administrator** (`GET`/`POST /updatelens/v1/settings`, `Rest\SettingsController`; see `docs/rest-api.md`): both need `manage_options` and the REST nonce; a save accepts exactly `{"site_checks":{"enabled":<bool>}}` as JSON (other keys, strings, numbers, form or query values: 400, nothing changes) and stores `enabled`/`disabled` with `Settings::save()` (not autoloaded), answering with the value read back (`500 updatelens_settings_not_saved` if it does not match). Responses keep the saved preference (`enabled`) apart from what may run (`effective`, `restriction: "filter"`); the filter can only keep checks off, never turn them on. Nothing enables site checks automatically (not activation, upgrades or the filter). Turning them off stops new sessions at once; started sessions expire, late reports are refused (`disabled`) and those checks stay unavailable; stored results and history are never changed or deleted. The Settings screen never starts a check.
- **Sessions** (`SessionManager`, `CheckSession`): one per check per start, live `CheckSession::TTL` (120 s), bound to check, purpose (`before`/`after`), user, login session and target. A public 128-bit **marker** (session ID, echoed in responses) and a private 256-bit **secret** (needed to report); neither is stored: the transient key is `updatelens_sc_` + SHA-256 of the marker and the record (`Storage\SiteCheckSessionCodec`) holds a SHA-256 of the secret. Reports are single-use: the session is claimed (`delete_transient()`) before the result is built, so replays and concurrent submissions get `session_unavailable`/`already_reported`; an invalid report does not use the session up. A missing, evicted, unreadable or expired session is unavailable: no marker, no accepted result, never a pass. `RateLimiter`: 12 starts per user per 10 minutes (user meta `updatelens_site_check_starts`, a list of integers).
- **Markers** (`FrontendMarker`): only for a well-formed marker of a live session of that check. Homepage: the request must be the homepage itself (empty path, no query variables, so `/?p=1` with plain permalinks is never marked) and anonymous (`is_user_logged_in()` false: a browser that sends cookies despite `credentials: 'omit'`, e.g. Playwright's WebKit on Windows, gets the signed-in render, which stays unverified, never a pass); sends `X-UpdateLens-Check` and `Cache-Control: no-store, …, private`, defines `DONOTCACHEPAGE` and prints `<span hidden data-updatelens-check="…">` last in `wp_footer`. REST: `/wp/v2/users/me` with the `X-UpdateLens-Check` request header, errors included. Keep the `nocache_headers` filter (`FrontendMarker::no_store_headers`): WordPress 6.2 sends no-cache headers without `no-store` again after UpdateLens (Ajax die handler, REST server). Ordinary requests cost one `isset()`; malformed markers no lookup; the front end never reads the opt-in option. Page caches that answer before WordPress cannot be bypassed: missing or stale markers stay inconclusive.
- **Browser runner** (`src/admin/site-check/`: `contract.ts` fixed checks, limits and strict start-response parsing; `observe.ts` one request → ReportValidator facts; `runner.ts` `runSiteChecks()`). No React, no strings; called by the baseline scheduler with `before` and by the update follow-up with `after` and the analysis ID (sent as `analysis`). Homepage: `credentials: 'omit'`, `cache: 'no-store'`, `redirect: 'manual'`; REST: `credentials: 'same-origin'` with the `wp_rest` nonce and the marker header. Only server-issued URLs on the page's own origin (cross-origin, mixed content, other markers: `not_run`); the secret only in the report POST body. Per attempt a timeout from the start response (10 s); one retry after 5 s unless the attempt passes. `attemptPassed()` mirrors PHP's pass rule for that decision only (shared cases in `tests/fixtures/site-check-attempts.json`, read by PHPUnit and Vitest); PHP's verdict is the result, and a failure followed by a pass is `inconclusive`/`unconfirmed`, never a pass. The homepage body is scanned in chunks and never kept; past `MAX_HOME_BYTES` (REST: `MAX_REST_BYTES`) the fact is `unread` → PHP `not_inspected` (inconclusive). Checks are independent (`Promise.all`, errors contained per check). Outcomes keep browser failures apart from verdicts: `reported` (PHP verdict) | `report_failed` | `expired` (no attempt started that could not be reported before the session ends; counted from before the start request) | `not_run` | `cancelled` (an `AbortSignal` aborts requests and timers, nothing more is reported). The start response gives REST the expected `user` (the signed-in user; the report is still checked against the session).
- **BEFORE baselines** (`Baselines`, PHP owns every freshness rule): the latest accepted BEFORE run per (administrator, WordPress login session, check), one non-autoloaded option row each (`Baselines::STORAGE_PREFIX` + SHA-256 of that identity; UpdateLens prefix, so never in snapshots) holding `SiteCheckResultCodec` JSON (no URLs, cookies, bodies, headers, nonces, markers or secrets; times are the server's, never re-stamped). Rows are read and written with SQL only (`OptionBaselineStore`: `INSERT IGNORE`, compare-and-set on the exact bytes), never the options API or object cache. **Latest wins by session start**, whatever the verdict (a newer failure must not hide behind an older pass); an older run never replaces a newer one, out-of-order reports included (`superseded`). Each check is stored and judged alone: a slow or failed REST run never touches the homepage baseline. Readiness per check (`readiness()`): `ready` up to `MAX_AGE_SECONDS` (600, = CheckComparator) for the current definition version and target, due for a refresh from `REFRESH_AFTER_SECONDS` (300); `expired`; `missing` (also unreadable, foreign or another target/version); `outdated` (its run started during an update or before the latest updater activity: it can never be attached, so it is due). In-progress runs have no row. Saving removes expired or unreadable rows of every user (bounded); `uninstall.php` removes all. No cross-user or cross-login reuse.
- **Start/report for BEFORE**: a `before` start needs a plugin update other than UpdateLens (else `not_needed`/`no_updates`) and no running update (else `not_needed`/`update_in_progress` with `refresh_in` = `RETRY_AFTER_FAILURE_SECONDS`), and opens sessions only for due checks (none due: `not_needed`/`fresh`, nothing counted against the rate limit); `before` responses carry `refresh_in` per check. An accepted `before` report is saved (`baseline`: `saved`/`superseded`); if it cannot be stored the report fails with `unavailable`.
- **Where baselines run** (`BaselinePage`, `AdminAssets::enqueue_site_check_baseline()`): only `plugins.php` and `update-core.php`, opt-in on, `update_plugins`, single site, not in maintenance mode, a login session and a relevant update (`get_plugin_updates()`, UpdateLens excluded); anywhere else nothing is enqueued and no request is sent. Settings are nested (`schedule.refresh_after`, `retry_after_failure`, `refresh_in`) so `wp_localize_script()` keeps them numbers.
- **Baseline scheduler** (`src/admin/site-check/baseline.ts`): event-driven, never polling: on load and when the page becomes visible again (`visibilitychange`, `focus`, back/forward cache), only while visible and only for checks due by PHP's `refresh_in`. After a run: reported → due in `refresh_after`; not issued → the server's `refresh_in`; failures → `retry_after_failure` (rate limits: `retry_after`); `disabled`/`forbidden`/`invalid_nonce`/`no_updates` stop the page; permanent target problems stop that check. Never in the way of an update: no click handlers; a run starts only `START_GRACE_MS` (750 ms) after the page is parsed or becomes visible (`schedule()`, triggers coalesce), because aborting in the browser cannot stop PHP from finishing requests it received (measured: an update clicked while baseline requests ran took ~300 ms longer on PHP 7.4); `wp-plugin-updating` or any form submission drops a pending start, aborts the run and pauses starts for `UPDATE_PAUSE_MS`; no start while `updates.js` is busy. One run per browser (Web Locks, else a localStorage lease, else none); a `BroadcastChannel` shares due times and update starts between tabs. No DOM, focus or console output.
- **Updater activity ledger** (`UpdateActivity`, option `updatelens_update_activity` via `Storage\UpdateActivityCodec`: random `epoch`, `sequence`, running request tokens => start times; nothing about users, plugins or packages): every change is a compare-and-set on the exact bytes, so concurrent requests are strictly ordered (never by timestamps). `begin()` (the first updater download of a request; later downloads of the same request, e.g. translations after a plugin update, write nothing) increments and returns the state before it (`generation` = `epoch:sequence`, `others_running`, `at`); `end()` (that request's shutdown) increments again, so **a request moves the sequence exactly twice** (`advance()`); `current()` / `quiet_generation()` give the generation and whether an update runs (and create the ledger). A missing or unreadable ledger starts a new random epoch, so no earlier generation can ever match. Running entries older than `STALE_AFTER_SECONDS` (900) are dropped. Each check session records the generation at its start (`CheckSession`/`CheckResult` `generation`, session codec schema 2, now 3 with the AFTER analysis; result codec schema 2; older values are not decoded).
- **Attaching BEFORE baselines** (`Baselines::for_update()`, reasons and their order in `SiteCheck\BeforeReason`): decided once, in the update request, when the analysis is created, from what is stored then; no request, no waiting, never re-evaluated, so a report accepted after the update began is never attached. Per check, independently: same administrator and login session (the storage key), current definition version and target, accepted strictly before the update's ledger record (`at`), at most `MAX_AGE_SECONDS` before it, its run started with no update running, and **its generation equals the generation right before this update with nothing else running**: any other update in between (another plugin, another administrator, a queued update, the update this baseline was already used for) moved the sequence (`intervening_update`); a concurrent one gives `overlapping_update`. Inconclusive and failing baselines are attached as they are (verdicts are derived on decode, never stored), never as a pass. `SiteCheckObservation::read()` returns per check the decoded result or a reason (`not_captured`, `data_corrupt`, `unknown` are read-only).
- **AFTER runs** (`Update\SiteCheckAfter`, reasons in `SiteCheck\AfterReason`): only after a successful single-plugin update that the updating browser's follow-up settled (`completed` + `follow_up`; the settled snapshot is stored). The follow-up response names the analysis; the browser (`update-follow-up/afterChecks.ts`) starts it only if `updates.js` is idle and no update started since the follow-up was sent, one analysis at a time, and aborts it on `wp-plugin-updating`; never retried. `purpose=after` + `analysis` → `open()`: the analysis's owner, from the login session of its attached BEFORE results (`not_owner` otherwise), within `START_WINDOW_SECONDS` (60) of completion, once (`already_started`; claimed by compare-and-set), only the checks with a BEFORE result (none: `not_needed`/`no_baseline`, nothing claimed); otherwise `not_eligible`. AFTER sessions carry their analysis (`CheckSession` `analysis`, session codec schema 3) and the expected generation; a report is stored only in that analysis, for that owner, once per check (`after`: `saved`; else `already_reported`/`unavailable`). Sessions that cannot open after the claim store `rate_limited`/`session_failed`. A follow-up answered `not_ready` (premature: its request started before IMMEDIATE) names no analysis and gets no AFTER run (the analysis is settled later, `not_followed_up`).
- **Overlap protection is the server's, from the ledger**: this update moved it from its BEFORE results' generation G to exactly G + 2. The AFTER start must see G + 2 with nothing running, else nothing runs and `overlapping_update` (same epoch) or `update_order_unknown` (ledger recreated, unreadable or unwritable) is stored for the checks; each report must still see the session's generation, else its result is stored **with** that reason and never compared (`not_comparable`). The browser's view is never trusted. An update that begins during a check request has begun (ledger written) before the request's response, so before its report.
- **Unavailable stays unavailable**: nothing is written later to resolve a missing AFTER side; reads derive `pending` while it can still arrive (open analysis; completed within the start window; started within `CheckSession::TTL` + `REPORT_GRACE_SECONDS`) and then `not_started`, `not_reported`, `not_followed_up`, `settle_expired`, `analysis_ended`, `no_baseline` or `not_captured`. A missing result is `not_run`, never a pass; a failure followed by a passing retry, maintenance mode, caches and firewalls stay `after_inconclusive`. A complete outage that also takes down `admin-ajax.php` cannot be reported by the browser and reads `not_reported`.
- **Untracked update paths**: anything that changes plugin files without WordPress's upgrader (`upgrader_pre_download`): FTP/SFTP, git or host deploys, file managers, restores. Also sites where the tracker is not registered (multisite; a failed schema upgrade). Their changes cannot invalidate a baseline or mark an AFTER run as overlapping.

## Potential Impact rules

- **Evaluated, never stored**: `Report\PotentialImpact` (pure) runs on the report's decoded phases inside `AnalysisReadModel::report()` → `potential_impact`; rules read only `final`, the other phases only decide Action Scheduler applicability. No persistence, no extra capture or query, no new codec reads.
- **Three fixed rules**: `large_autoloaded_option` (Options; added/became autoloaded/grew past `LARGE_OPTION_BYTES` 150,000, an advisory size), `recurring_cron_event_removed` (WP-Cron; per hook, more recurring instances removed than added), `recurring_schedule_changed` (WP-Cron, Action Scheduler; recurrence configuration of a `changed` entry differs). Every rule and every non-finding case needs a test.
- **Site checks are evaluated beside the Net result, never as a phase** (`PotentialImpact::evaluate_site_checks()` on the report's `site_checks`, added by `AnalysisReadModel::report()` as `potential_impact.site_checks`): they never change `potential_impact.status`, `signals` or `findings` (Net result only, so finding indexes and deep links are unchanged). Findings come only from the comparison state and only from a verified pass before the update: `site_check_newly_failing` (`newly_failing`; `evidence.failure` = the AFTER result's reason) and `site_check_changed` (`changed` with `redirect_appeared`), each with the check's `before`/`after` sides as reported. Every check carries `change` (`redirect_appeared`, `redirect_disappeared`, `redirect_then_failure`, else null); `redirect_disappeared` and `redirect_then_failure` start from a redirect, not a verified pass, so they are compared observations without a finding (never "newly failing"). `passed_both`, `failing_both` and `recovered` are evaluated without a finding; `not_run`, `not_comparable` (an unconfirmed failure followed by a passing retry included) and `pending` are never findings and never "no findings". Per check `not_applicable` only for `disabled` and `not_captured` (`SITE_CHECK_NOT_USED`), ignored by the overall status like an absent Action Scheduler. `tests/fixtures/site-check-impact-cases.json` is real output for realistic cases (kept in sync by `SiteCheckImpactCasesTest`, regenerated with `UPDATELENS_WRITE_FIXTURES=1`); the UI tests render it.
- **Not evaluated ≠ no findings**: per signal `evaluated` + `finding_count`, or `not_evaluated` + the Net result phase's own reason (`finding_count: null`); overall `evaluated`/`partial`/`not_evaluated`.
- **Optional Action Scheduler**: `not_applicable` (reason `not_installed`) only when every Action Scheduler phase **stored** `not_installed_throughout` (absent at BEFORE, IMMEDIATE and SETTLED; `AnalysisReadModel` passes this to `PotentialImpact::evaluate()`); it never counts against the overall status. Never infer it from reported `not_installed` reasons: older analyses stored that after a phase's first capture only. Appearing (`newly_detected`), `no_longer_detected`, failures, corrupt data, expiry and historical `not_installed` stay `not_evaluated` (the UI says absence throughout is not confirmed).
- **Unchanged instances are invisible in diffs**: Cron removal evidence describes recorded changes only (`other_recorded_changes`); never add fields that claim a hook has (or has no) instances left.
- **Only real recurrence changes**: next-run rescheduling, Action Scheduler status, schedule renames with the same WP-Cron interval, unknown intervals and equivalent Action Scheduler cron notations (`equivalent_cron_expression()`) are never findings.
- **Structured evidence only**: codes, subject (option / hook / group), `evidence`, `before`, `after`, built from fields the decoded diffs already hold. No values, arguments, fingerprints, IDs, severities, scores or English text; presentation localizes "what changed / why it may matter / what to check". Findings are observations, never attributed to the updated plugin.

## Admin UI rules

- **React displays backend semantics; it does not recreate business logic.** Statuses, outcomes, phase availability and reasons come from the Reports API; React maps them to text (`src/admin/utils/labels.ts`) and never derives them from other fields (e.g. no deadline arithmetic, no recomputing diffs).
- **Phase wording stays observational/non-causal**: "During update", "After update", "Net result", "observed". Never "caused by", "created by <plugin>", "definitely".
- **API internals are never shown** as main text: raw status/reason/outcome codes appear at most under "Technical details". Server error messages are never rendered; `api/errors.ts` maps failures to fixed texts.
- **No option values exist in the UI** — only names, sizes and autoload state. Render only fields of the typed API contract (`src/admin/types/api.ts`).
- **Three levels inside the one UpdateLens menu**: History → a report's **overview** (`&analysis=<id>`, `pages/ReportPage.tsx` + `components/ReportOverview.tsx`) → one **signal page** per signal (`&signal=options|cron|action_scheduler`, `components/SignalDetail.tsx`). Overview and signal pages share one loaded report (no extra request) and the selected phase. **The overview is for understanding, signal pages are for inspection.**
- **The overview never renders change rows, lists or site totals** (Potential Impact finding rows are findings, not diff rows). Header (plugin name, status badge, versions, "Updated …", plugin file in muted monospace) → the compact status line, only while open or not fully completed (waiting with Refresh, partial, failed, …) → phase tabs → the update summary panel: headline ("3 observed changes", the tab's total) and plain observational sentences (`phaseSummarySentences()`: "Changes were observed in Options & autoload and WP-Cron.", "No changes were observed in …", "… was not available for this phase."; with no available signal the phase's reason from Options) → Potential Impact (below) → **one card per signal**, always in the order Options & autoload, WP-Cron, Action Scheduler (never abbreviated "AS"), each an `li` with an `h3` whose link (stretched over the card, described by the state) opens the signal page: "6 changes" plus the non-zero counts ("Added 3 · Changed 2"), "No changes", or "Not available" plus the reason's title → collapsed "Technical details" (which holds the phase note). Cards are entry points, never tabs.
- **A signal page** has a breadcrumb (`nav` "Breadcrumb": Update History › plugin › signal, `aria-current="page"`), the signal as `h2`, the report context (plugin, versions, status badge; the status line like the overview), phase tabs counting **that signal only**, then either the signal in full (`components/SignalParts.tsx`: a summary panel with the headline "6 observed option changes", counts and the signal's note; lists with `h3` titles; notes; quiet "Site totals" last) or a calm empty state (`noChangesText()` / the unavailable reason's title and description), and collapsed "Technical details" with only that signal's reasons. No signal tabs, no tab inside a tab, no reordering. Each signal's availability is independent; a phase is unavailable only if all signals are.
- **Hierarchy**: plugin name, versions, status, the selected phase, its total and the signal states come first on the overview; change rows first on a signal page, its counts second; site totals (bytes, option/event/action counts) are muted tertiary text, never equal cards; analysis ID, plugin file, observation outcome and timestamps stay in the collapsed "Technical details". The status is a badge plus, when not fully completed, a compact line with a tone accent, never a large colored box. **An expired observation is a "Partial report"** (badge, amber): `completed` + `settle_outcome: expired` from the API (the update succeeded, the post-update state was not captured). The same badge text on History, the overview and signal pages; failed updates stay "Failed", the stored status is unchanged.
- **Recorded does not mean changed.** Phase tabs show a pluralized count ("Net result 4 changes", `_n()`; accessible name e.g. "Net result, 4 changes") or "Not available", signal cards "4 changes", "No changes" or "Not available"; History shows "Changes observed", "No changes" or "Not available" per phase, never a checkmark for "recorded". Counts are derived only from summary record counts (`utils/changes.ts`: added + removed + changed, plus rescheduled for WP-Cron and Action Scheduler), never from deltas; an unavailable signal is `null`, not 0. Phase counts sum the available signals; History's phase state includes Action Scheduler (changes if any recorded signal has changes).
- **Defaults prefer changes**: the first phase with changes (Net result, After update, During update), else the first available (Net result, During update, After update), computed from the whole report so the overview and every signal page open the same phase. Never open an empty phase when another available one has changes.
- **Successful analyses without changes use compact states** ("No tracked changes observed during this phase" on the overview, "No changes" on a card, a calm empty state such as "No option changes observed" on a signal page): no all-zero counts, empty lists or notes. Empty lists are left out of signals with changes (the summary shows the zeros). Never hide a phase (During update stays, even when usually empty).
- **Long diff lists collapse, not virtualize**: `DEFAULT_VISIBLE_DIFF_ROWS` (10) rows per list, then a real button ("Show 37 more changed options" / "Show fewer …", `aria-expanded`, focus stays on it). Totals stay in the titles. No pagination inside a report.
- Added/removed option rows show "Autoload: On/Off" plus the stored value only when it says more (`auto`, `auto-on`, `auto-off`); explicit `on`/`yes`/`off`/`no` would only repeat the label.
- **Changed options are dense**: one "Value changed · size" line; autoload setting/behavior rows only when `autoload_value_changed` or `autoload_behavior_changed`. Byte pairs that would round alike ("6 KB → 6 KB") get two decimals (`formatBytesPair`); the exact signed delta stays visible.
- **Ownership is never guessed.** No "likely plugin-related"/"other activity" grouping, filters or prefix heuristics; every observed record is shown, including cache-like options (e.g. `_wpforms_transient_*`), other plugins' jobs and core jobs.
- **WP-Cron in the UI**: hooks in monospace, never arguments or fingerprints. Rescheduled events are shown by default but with less emphasis than added/removed/changed, never as a warning or problem. WordPress core and unrelated jobs are never hidden or filtered; no ignore lists, no ownership, no risk wording.
- **A removed one-time WP-Cron event is "No longer scheduled"** ("Previously scheduled for …"): it may have run or been unscheduled, which UpdateLens cannot tell apart, so never "ran", "executed", "completed" or "deleted". Recurring removals stay "Removed". The summary card counting both says "No longer present". This is wording only; the API category stays `removed`.
- **WP-Cron notes appear only when relevant**: the hidden-arguments note when events are listed; "One-time jobs may disappear…" only with a one-time disappearance; the moved-one-time note only with a rescheduled one-time event.
- **Action Scheduler in the UI** (`components/ActionSchedulerDiff.tsx`, the only place that renders its diffs):
  - **`not_installed` is not an error**: "Action Scheduler not detected / Action Scheduler was not active for this phase." Never "error", "failed" or "broken" for it.
  - **Active-state diffs are not execution history**: wording says the signal compares active (pending or in-progress) actions. No UI for completed actions, logs, claims or execution history.
  - **Removed actions are "No longer active"** (section, row and summary card; "Previously scheduled for …"): they may have run, been canceled or left the queue otherwise, so never "completed", "canceled", "deleted" or "ran". The API category stays `removed`.
  - Hooks in monospace, group as secondary metadata ("Group: woocommerce"). **A group is never ownership**: no "WooCommerce action", "owned by", grouping or filtering by group or prefix. Other plugins' actions in the window are always shown.
  - Rescheduled actions are quiet, never warnings. Durations use `formatDuration()` (UpdateLens translations), never browser-locale unit words. Cron expressions are shown as stored, never paraphrased.
  - **Arguments and fingerprints never reach the UI**. With rows listed, the hidden-arguments note and the between-capture note are shown ("Very short-lived actions that are queued and completed between captures may not appear."); the leave-the-queue note only with a no-longer-active action. No notes in the compact no-changes state.
- **Potential Impact on the overview** (`components/PotentialImpact.tsx`, wording in `utils/impact.ts`): a section between the update summary and the signal cards, labelled "Based on Net result" and the same whatever phase is selected: with another phase selected and an evaluated result, a callout before the findings says so ("You are viewing During update. These findings do not come from that phase …", plus "Show the Net result phase" when the Net result has data); without a Net result the headline explains instead. It renders the API's evaluation, never recomputes it: states from `status` and the Options reason (findings, none, waiting, expired, unavailable). **Progressive disclosure**: findings are grouped by rule and signal, and every group starts as one compact row (title + count in an `h4` button with `aria-expanded`, signal, the first two option names or hooks with "and n more", one short evidence-based line from `groupSummary()` as the button's description: the stored data now autoloaded ("Now autoloaded across these options: 492 KB, up 374.8 KB"; `autoloadedBytes()`: each option's stored size counted only while its effective autoload behavior is on, added options as zero before; never the site's total or memory; "up from <before>" when the change would round to the current value, "all newly autoloaded" when nothing was before), or the instances no longer observed, or the kind of schedule change, plus one next step; never the review size or other long explanations; the whole row toggles). A group's details render only while expanded (never hidden DOM): "What changed" (one row per finding: identifier, summary sentence, before → after values, a "View in <signal>" link whose `aria-label` names the item), above the rows, for several findings, `groupFacts()` (rows "Now autoloaded across these options", "Autoloaded before the update", "Change in autoloaded stored data", plus the stored size, autoloaded or not, when it differs; pairs that would round alike get two decimals; notes on added or newly autoloaded options and that the figures cover only these options; instances across hooks); then "Why it might matter" and "What to check next" once per group, worded for one finding or several (`_n()`, "each of these options", "each hook"; several items are never presented as one plugin's); `DEFAULT_VISIBLE_FINDINGS` (3) rows, then 50 at a time with "Showing n of m", focus moving to the remaining reveal button when the pressed one disappears. Expanded groups and "What was checked" live in the report page's state, so they survive a visit to a signal page; back on the overview, focus returns to the finding link that was opened. Checks that did not run stay visible as a compact amber list (per signal "Not checked (unavailable | failed | observation expired) · <reason>", "Not checked yet (waiting for the settled capture)"; categories from `checkCategory()`), never only inside a disclosure. Everything else is in the collapsed "What was checked": per signal "Checked · n findings", "Not applicable" or the incomplete status with the reason's description, the patterns checked, and what a result does not show. Zero findings: a headline by completeness ("No findings matched the completed observations.", see Site checks in Potential Impact) plus that only a few patterns are checked. No severity, score or verdict wording ("safe", "no issues", "no conflicts", "risk-free", "healthy"). Removed recurring WP-Cron events are "no longer observed", never "stopped running"; Action Scheduler schedule changes never claim a frequency direction. On phones the group's signal icon is hidden (the signal is named in the row); long names are truncated in collapsed rows (full name in the text and `title`) and wrap in the details; sizes keep number and unit together (`keepTogether()`).
- **Site checks in Potential Impact** (wording in `utils/siteCheckImpact.ts`; rows reuse the group row shell `CompactRow` and `Guidance`): site check findings come first in the findings list, one compact row per check (title such as "Homepage check newly failing" or "Homepage now redirects", source "Site checks · Homepage", one observed fact plus one next step: "Homepage returned HTTP 500 twice after the update. Check whether it is accessible now."). Expanded: "What changed" (the earlier and the later observation in one sentence, then "Earlier check" / "Later check" with the verdict, the check's own time and its age or delay relative to the update, and every request: HTTP status or "No response within 10 seconds", "WordPress verified" / "Not verified as WordPress", completion marker or REST body, duration), "Why it might matter", "What to check next"; no link (there is no signal page). The label is "Based on Net result and site checks" once a check was compared, and the other-phase callout then names site checks; counts and headlines include site check findings. Wording reports observations only: timeouts never mean "down", unverified responses are never attributed (to WordPress, PHP, the host or the plugin), a redirect is a changed response, not a failure, and its destination is never shown (the browser cannot see it); a pass never means the site works. Checks used but not compared, or still pending, are in the amber list ("Homepage check: Could not be compared · <reason>", "Still pending"); "What was checked" lists both checks ("Passed at both observation points", "Newly failing", "Changed" (with the `change` as an observation when it is not a finding), "Already failing at the earlier observation", "Recovered", "Could not be compared", "Still pending"; compared checks with their earlier/later timing), or one quiet "Site checks" row for `disabled` ("Not used") and `not_captured` ("Not captured"), never a warning on old reports. Reasons map to fixed sentences per side (BEFORE, AFTER, comparison); inconclusive runs name their verdict reason ("one request failed and the retry did not confirm it"). **Zero findings are worded by completeness** (`impactCompleteness()`, from the API's statuses only): "No findings matched the completed observations." (everything applicable completed; site checks that were off or not recorded do not count), "No findings yet — site checks are still pending.", "No findings in completed observations; some checks were unavailable." Pending or unavailable checks are never presented as passed.
- **Pending site check results refresh in place** (`hooks/use-pending-refresh.ts`, used by `ReportPage`): only while the API says a site check is `pending`, the open report is re-read through `GET /analyses/{id}` every 5 s (`PENDING_REFRESH_INTERVAL_MS`), one read at a time, none while the document is hidden (the next read runs when it is visible again), at most `PENDING_REFRESH_MAX_REQUESTS` (36) reads or `PENDING_REFRESH_MAX_FAILURES` (3) failed reads in a row per run, stopping when nothing is pending or the view unmounts. The newer report replaces the loaded one without remounting: the selected (or first default) phase, expanded findings and focus are kept; failed reads keep the current report and show nothing. Potential Impact shows "This report checks for the pending site check results every few seconds while it is open." or, once stopped, "Automatic checking stopped; …" with the same button ("Check now" / "Check again", starts a new run); a `role="status"` line announces "Site check results arrived."; if the button had focus when the line disappears, focus moves to the section title. Completed, disabled and historical reports are never re-read. No WebSockets, no backend polling service, no schema.
- **Locating a finding's rows**: finding links open the signal page on the Net result with `&item=<name>` (`&group=` for Action Scheduler, `&kind=added|removed|changed` for the list the finding is about, `&finding=<index>` in `potential_impact.findings`). `utils/highlight.ts` (`locate()`) matches rows by the finding's evidence, by record identity (`ChangeRow record`): **exact** ("From Potential Impact", tinted, primary left rule) only when the evidence identifies them (an option by name; a WP-Cron removal's listed recurring instances; a schedule change's before/after values matching exactly one row); otherwise **group** (neutral gray rule, "Same hook as the finding"): rows that match alike (entries of one hook can differ only in hidden arguments) or, without a matching finding (stale index, older link), all rows of the hook in that list. Never imply a row is the finding's own when the evidence cannot tell. The notice says which (`ambiguous`). `DiffSection` starts expanded when a marked row would be hidden, the first located row is scrolled into view, and a "Clear highlight" notice sits above the phases. Choosing another phase drops the item. Nothing is filtered or reordered.
- **UTC API timestamps are localized only in presentation** (`Intl.DateTimeFormat`, browser time zone); **backend byte counts are formatted only in presentation** (`utils/format.ts`, 1 KB = 1024 B). Never change the values sent by PHP.
- **No risk classification** (impact levels, "safe"/"dangerous", size thresholds) without an explicitly designed model.
- Navigation is URL state on the admin page via the History API (`utils/route.ts`); no router dependency. `&analysis=<id>` (overview), `&signal=<signal>` (signal page), `&phase=<phase>` (only once a phase was chosen; otherwise the default), `&paged=<n>` (History page, kept for the way back), `&item=`/`&group=`/`&kind=`/`&finding=` (a located finding on a signal page). Opening a report, a signal page or the overview pushes an entry (Back/Forward work); choosing a phase replaces the current one. Unknown `signal`/`phase` values fall back to the overview/default phase, so older report URLs keep working. After in-app navigation focus moves to the new view's `h2`; a phase change keeps focus on its tab. The screen is a top-level menu page (`add_menu_page()`, `dashicons-visibility`, slug `updatelens`) at `AdminPage::MENU_POSITION` 65.5, directly below Plugins (65) and above Users (70); WordPress resolves collisions, `$menu` is never touched. On single sites it has two entries (`add_submenu_page()`): "Update History" (the top-level page itself, same slug) and "Settings" (`AdminPage::SETTINGS_SLUG`, `updatelens-settings`, its own wp-admin page; Multisite has no Settings entry). Both render the same shell (`<h1>UpdateLens</h1>`, root `data-view="reports|settings"`, read by `main.tsx`); only the History screen marks reports as seen and repairs the table. The Settings hook suffix (screen ID, `pagenow`) comes from the top-level menu title, so it changes with the new-reports count and translations: hook and enqueue by the suffix `add_submenu_page()` returned (`AdminPage::$settings_hook_suffix`), never by a literal screen ID.
- **Settings screen** (`pages/SettingsPage.tsx`, API `api/settings.ts`): `h2` "Settings", one section "Site checks" (`h3` plus a badge of the **stored** state: "On", "Off", or "Off for this site" only when the saved preference is on and `restriction` is set; never "active"), one labelled checkbox "Check site responses around plugin updates" with its description (`aria-describedby`), and a conventional "Save settings" button: toggling never saves; "Unsaved change" until saved; while saving the button reads "Saving…" (`aria-disabled`, a synchronous guard drops repeated submits and the checkbox cannot change); success is a `role="status"` sentence worded from the stored state, failure a `role="alert"` with fixed text (server messages never shown) that keeps the stored badge and the admin's choice for a retry. A host restriction names the filter: with the preference on, an amber note says no checks run; with it off (the administrator's own choice), the badge stays the neutral "Off" and one quiet line says turning checks on would have no effect. "How site checks work" is a collapsed `<details>` (what is checked, when checks run, what to know: observations not proof, caches and restrictions, extra requests in logs, only response facts stored, not whole-site or uptime monitoring). An unexpected API response is a failure, never a guessed state. The screen sends one settings read and no site check requests. WordPress styles checkboxes, but the scoped CSS reset removes their border, so the checkbox sets its own.
- **Menu count of new reports** (`Admin\UnreadReports`, rendered by `AdminPage::add_page()`): WordPress's own count bubble (`awaiting-mod`/`pending-count`, "99+" above 99, screen-reader text "3 new UpdateLens reports"), only for users with `Plugin::CAPABILITY`, single site only. It counts History entries (every analysis row) with an ID above the user's watermark: one primary-key `COUNT(*) … WHERE id > %d`, never diffs. Watermark = user meta `updatelens_last_seen_analysis_id`, never below the option `updatelens_unread_origin_id` (the newest ID when tracking started: 0 on activation of a fresh install, the current maximum on sites that already had reports, so old reports never count as new). Loading the UpdateLens History/report screen (any view; not Settings) sets the user's watermark to the newest ID before the menu is built; it only moves forward and is per user. Only IDs are stored. Failures show no count and never break the admin. Deactivation keeps both; `uninstall.php` deletes the option and the meta of all users. No REST route, no polling.
- **First run** (no analyses): onboarding replaces the History (`components/FirstRun.tsx`): steps, one "Go to Plugins" link (URL from PHP, only for users who can open it), the three signals (Options & autoload, WP-Cron, Action Scheduler), privacy and observation notes, and the monitoring start with the baseline plugin list (alphabetical, collapsed after 10, Active/Inactive as text). No "scan"/"start" buttons: nothing is started manually. If baseline data is unavailable, a fallback sentence replaces it without an error. Once an analysis exists, onboarding disappears.
- The History boundary ("Monitoring began on … Updates before this point were not observed by UpdateLens.") appears only on the last History page, after the oldest analysis, and only when the start is known.
- Frontend tests (Vitest + Testing Library, jsdom) live in `tests/admin/` (not `src/`, which ships in the release ZIP); mock `@wordpress/api-fetch` with API-shaped fixtures.

## Working rules

- Make focused changes that do what the task asks. Don't add features outside the requested task.
- Avoid unrelated refactors, renames or dependency upgrades.
- Add PHPUnit tests for business logic as features are introduced (`tests/Unit/`, mirroring `includes/`). Unit tests don't boot WordPress: keep logic in pure classes that take plain data, and keep `$wpdb`/WordPress calls in thin wrappers.
- Run the relevant checks before finishing (below).

## Gotchas

- CSS is scoped: `postcss.config.cjs` prefixes every selector with `#updatelens-root` (`:root`/`html`/`body` become the root itself). Radix/shadcn components that portal to `document.body` lose their styles — portal into an element inside the root.
- The root id `updatelens-root` is shared by `Admin\AdminPage::ROOT_ID`, `src/admin/main.tsx` and `postcss.config.cjs`.
- A stale `assets/admin/dist/vite-dev-server.json` (dev server killed uncleanly) makes a site with the dev helper load from `localhost:5173`. Delete it or run `npm run build`.
- Bump versions together: `package.json` (+ `package-lock.json`), `updatelens.php` (header + `UPDATELENS_VERSION`), `readme.txt` Stable tag. The release script enforces this. Public releases use plain `X.Y.Z` (WordPress.org Stable tag: numbers and periods only); betas were pre-releases of the next minor (`0.2.0-beta.1`, see `docs/private-beta-release.md`). The plugin version is independent of `StorageSchema::VERSION`.

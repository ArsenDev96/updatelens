# 0.3.0 final release artifact

Status (2026-10-19): **open**. The existing 0.3.0 ZIP predates `main`, so no validated ZIP of the current `main` exists. WordPress.org submission stays on hold until the owner approves a final ZIP.

This note records the discrepancy and the steps to produce and validate the final artifact later. It does not claim that any current check passed: nothing listed here was rebuilt or run on 2026-10-19.

It was added on the branch `plan/0.4.0`, in a documentation-only commit directly on top of `f531c26`, so it can be cherry-picked onto `main` without any 0.4.0 code. The later commits on `plan/0.4.0` contain **unreleased 0.4.0 code** (from P1 on: the Dashboard → Updates follow-up). That code is not part of 0.3.0 and was never part of its validation, so 0.3.0 is never built from `plan/0.4.0` or any other 0.4.0 branch (step 1).

## Steps to produce the final artifact

Run these only when the owner asks for the final build. Record every result (command, versions, pass/fail, output summary) in this file or the release notes. A step that was not run is reported as not run.

1. **Choose the commit.** The intended 0.3.0 release commit on `main`: currently `f531c26`, or a later `main` commit only if the owner approves further 0.3.0 changes. Never a commit of `plan/0.4.0` or another 0.4.0 branch, which contain unreleased code. Before building, confirm that the commit is on `main` (`git merge-base --is-ancestor <commit> main`) and that `git log --oneline f531c26..<commit>` lists only approved 0.3.0 changes. Check that `package.json`, `package-lock.json`, the plugin header, `UPDATELENS_VERSION` and the `readme.txt` Stable tag all say `0.3.0`. Check that the `readme.txt` changelog and "Tested up to" match what will actually be tested.
2. **Preserve the old ZIP first.** `scripts/release.mjs` deletes the whole `release/` folder before it builds, so copy `release/updatelens-0.3.0.zip` outside the repository (e.g. next to the earlier release-candidate backups) before building.
3. **Start from a clean tree** at the chosen commit (`git status` empty), then `npm ci` and `composer install`. On a machine without PHP, run Composer in Docker.
4. **Automated checks**, all fresh:
   - `composer validate --strict`
   - `composer lint`
   - `composer test` on PHP 7.4
   - `php -l` on the newest PHP with all deprecations reported
   - `npm run check`, `npm test`, `npm run build`
5. **Build**: `npm run release` (set `COMPOSER_BIN` when Composer runs in Docker). Record the ZIP's size and SHA-256.
6. **Package audit**: compare the ZIP contents with the `INCLUDE` allowlist in `scripts/release.mjs` and the release-package audit in `docs/private-beta-release.md`. It must contain no tests, `docs/`, `dev/`, `languages/`, source maps, `vite-dev-server.json` or dev Composer packages.
7. **Static release checks**: Plugin Check on the exact ZIP, on a native disposable site (WordPress 6.3+ is needed for Plugin Check; never Playground), with zero errors and warnings. Then the official `readme.txt` validator.
8. **Runtime matrix** on disposable sites (never a real site), using the test matrix in `docs/private-beta-release.md`:
   - clean installs on WordPress 6.2 / PHP 7.4 and WordPress 7.1 / PHP 8.x;
   - an upgrade from `0.2.0-beta.2` (rebuilt from commit `62b9fcb`, since no beta.2 ZIP is kept);
   - a real "Update now" with website checks enabled, a failed update, and an expired observation;
   - privacy (a fake secret is never exposed), `WP_DEBUG` hygiene, and uninstall.

   Disable core automatic updates on old-WordPress test sites, so they stay on the version under test.

9. **Owner review**: hand over the ZIP, its SHA-256 and the recorded results. Submission to WordPress.org happens only after the owner's explicit approval. No tag, GitHub release or SVN commit before that.
10. **Update `CLAUDE.md`** (Project status) with the validated commit and ZIP hash, replacing the unverified statement.

Status (2026-10-19, branch `plan/0.4.0` from `main` at `f531c26`, 0.3.0, schema 7):

- **P1 is implemented and committed on this branch** (`9a2c735`). See [P1 status](#p1-status-implemented) for what was built and what was validated.
- **P2 is implemented on this branch** (the commit after `ba6288c`) as an **internal foundation only**: multi-plugin updates are still not analyzed unless a development constant is defined. See [P2 status](#p2-status-implemented-internal-only) for the boundary, what was built and what was validated.
- P3–P7 are planned only.
- Proposed names (classes, columns, codes, constants) may change during implementation. The rules in `CLAUDE.md` stay authoritative until a phase changes them deliberately.

WordPress.org submission of 0.3.0 stays on hold until the owner approves a final ZIP. The existing 0.3.0 ZIP predates `main`; see [0.3.0-final-artifact.md](0.3.0-final-artifact.md). Do not merge 0.4.0 work into `main` before that is settled, so that `main` still describes the 0.3.0 release candidate. From P1 on, this branch contains **unreleased 0.4.0 code**: a 0.3.0 rebuild uses its intended release commit on `main`, never this branch (step 1 of that note).

## Scope

Confirmed:

- Automatic (background) plugin updates, recognized by WordPress's automatic updater itself, whatever runs WP-Cron (also `wp cron event run` under WP-CLI; see [Recognizing automatic updates](#recognizing-automatic-updates)).
- Bulk plugin updates, including Dashboard → Updates.
- PHP fatal error detection and reporting.
- Additional website checks: the login page only, initially.

Excluded:

- Email alerts or any other notification channel.
- Direct WP-CLI plugin updates (`wp plugin update`).
- Website checks for queued updates on Installed Plugins (several "Update now" in a row, or the bulk action with JavaScript): they stay "not compared".

Unchanged from 0.3.0:

- Multisite is not supported.
- Themes, core and translations are not analyzed; they still move the updater activity ledger.
- Updates of UpdateLens itself are not analyzed.
- No telemetry and no outbound requests by UpdateLens.

## Principles carried into 0.4.0

- UpdateLens observes the updater and never owns it. Filters return their input, every callback catches `Throwable`, and an observation that does not fit the memory **or time** budget is skipped, never forced.
- Observations, not causes. Nothing says a plugin "caused", "broke" or "created" anything. A batch-level observation is never attributed to one plugin, and a PHP error's file location is a location, not a cause.
- Unavailable is not "no change", Not assessed is not "nothing found", a missing check is never a pass, and no recorded error is never "no errors".
- PHP owns every rule, status, reason and count. React renders the API.
- Fixed codes, never stored messages, paths, URLs or values. Every new record is bounded.
- UI labels stay: "Configuration changes", "Informational", "Not assessed", "High priority" (and "Needs review").
- Every new finding states **what was observed** (with its time and phase), **why it may matter**, and **what to check next**, without claiming causation.

## 1. Bulk updates (P1–P3)

### Terms

- **Update request**: one PHP request in which WordPress's upgrader runs.
- **Batch**: the plugin updates UpdateLens analyzes within one update request. Ajax "Update now" is a batch of one (unchanged).
- **Plugin analysis** (item): one plugin within a batch, with its own BEFORE and IMMEDIATE captures.
- **Batch analysis**: the observation of the whole batch, from before its first plugin to the settled state after it.

Queued updates on Installed Plugins (several "Update now", or the bulk action with JavaScript) are several update requests, so several batches of one. They keep their 0.3.0 behavior: per-plugin After update phases, each settled by the next update (`next_update`), and website checks not compared (D6).

It reuses the existing completion mechanism unchanged: `updatelens_settle`, `PluginUpdateAnalyzer::settle_follow_up()`, the AFTER start from the follow-up response, and every server-side rule (nonce, `update_plugins`, owner, strict plugin list, request start after IMMEDIATE, window, compare-and-set).

Remaining P1 limitations:

- **Small timing margin.** The follow-up relies on the iframe's `load` firing after the update request's shutdown work ended (F12: 32 ms on 6.2 / PHP 7.4). On a host that ends the response before PHP's shutdown work finishes (`fastcgi_finish_request()`-style servers), the AFTER start can see the update still running. The server then stores `overlapping_update` and the check is not compared. It never produces a false pass. Not observed on the tested stacks.
- **No readiness state on Dashboard → Updates.** That screen keeps its fixed note (now "compared only for updates of a single plugin"). Users must know the checks before the update are ready from Installed Plugins; the background checks before the update still run on both screens.
- **Leaving the iframe early.** If the user leaves the update page before it finishes loading, nothing is sent; the analysis settles on a later admin page (`not_followed_up`), as before.
- The non-JS single update link (`update.php?action=upgrade-plugin`) is not part of P1 and behaves as before.

### Capture points in a multi-plugin batch (P2)

For `bulk_upgrade()` with N > 1 plugins in one interactive wp-admin request:

| Point              | Hook (UpdateLens at `PHP_INT_MAX`)                   | Snapshot                               | Notes                                                                                                                                                                                                                                                         |
| ------------------ | ---------------------------------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Batch begin        | `upgrader_pre_download` of the first analyzed plugin | B₀ = BEFORE of item 1 and of the batch | Earlier awaiting analyses are settled first (existing `next_update` rule).                                                                                                                                                                                    |
| Item _i_ installed | `upgrader_install_package_result` of item _i_        | Sᵢ = IMMEDIATE of item _i_             | No per-plugin `upgrader_process_complete` exists in bulk (F3). Files are replaced; PHP still runs the old code.                                                                                                                                               |
| Item _i+1_ begins  | `upgrader_pre_download` of item _i+1_                | BEFORE of item _i+1_ = **Sᵢ, reused**  | Nothing UpdateLens attributes happens between them in `bulk_upgrade()`. Reusing Sᵢ gives N+2 captures instead of 2N+1. Changes made by other plugins' `upgrader_pre_download` callbacks for _i+1_ land in _i+1_'s During update, which is when they happened. |
| Batch end          | the bulk `upgrader_process_complete`                 | E = IMMEDIATE of the batch (P3)        | After core's handlers, other plugins' reactions and translation updates (F4). P2 captures nothing here (no batch record to store it in), so P2 takes N + 1 captures, not N + 2.                                                                               |
| Batch settled      | a later request (P3)                                 | SETTLED                                | Page-mode follow-up from the iframe (P1's mechanism, naming the batch), admin page, next update, else expired.                                                                                                                                                |

Captures are read-only (SELECT), so they are safe at any of these points. The risks are memory and time:

- **Memory**: `ObservationBudget` is asked before every capture (exists). The batch begins only if a whole observation fits, as today. Between boundaries only the encoded JSON of Sᵢ is kept, not the decoded snapshot.
- **Time (new)**: a batch takes N+2 captures inside a request that already downloads and unpacks N packages, under maintenance mode. A PHP or web-server timeout would stop the batch half-way with maintenance mode on, which UpdateLens must never cause.
  - Proposed `Update\CaptureTimeBudget`: measure every capture's duration in this request and allow the next capture only while the cumulative capture time stays under a cap.
  - The cap is the smaller of a fixed ceiling and a fraction of `max_execution_time` when it is set. Exact values are measured in P2.
  - When the budget runs out, the remaining items end `failed` / `analysis_error`, the batch records no batch-end capture, and the update itself continues untouched.
  - `set_time_limit()` calls by core restart PHP's timer, and web-server timeouts are invisible to PHP, so the cap must be absolute and conservative, not "remaining time".

### P2 status: implemented (internal only)

**Boundary.** Public behavior is unchanged: without the constant `UPDATELENS_INTERNAL_BATCH_ITEMS` (defined `true`, e.g. in `wp-config.php` of a disposable site), multi-plugin updates are ignored exactly as in 0.3.0 and P1. P2 is a checkpoint for review, not a feature. With the switch, each plugin of a multi-plugin update gets its own analysis row, but the reports would be **misleading or unfinished** if shown to users:

- N History entries and N new reports in the menu count for one batch (D5 asks for one entry per batch);
- each plugin reads "Update completed" with After update and Net result unavailable, explained in the UI as "not recorded" (the UI has no wording yet for `batch`, `batch_update` or `capture_time_budget`);
- no Potential Impact on any Net result, and no website checks for these updates.

So the switch stays off on every real site until P3 adds the batch record and its presentation.

**Deviations from the design above, and why.**

- **Items stay `captured` until the batch ends** (the design had `awaiting_settle` at Sᵢ). An `awaiting_settle` row can be settled by any other request while the batch still runs: an admin page in another tab, a follow-up, or a report read that expires it. Its After update would then include the next plugins' installs. A `captured` row is left alone by other requests (unless stale, after 15 minutes), so Sᵢ is written as its During update without a status change.
- **No IMMEDIATE snapshot is stored for items.** Sᵢ is handed to the next item in memory, as encoded text only (options, WP-Cron and Action Scheduler columns), and only when it was stored and nothing else was downloaded in between; otherwise the next item takes a fresh capture.
- **No batch-end capture E in P2**: it belongs to the batch record (P3).
- **The batch's own codes (`batch_interrupted`, `updatelens_updated`) wait for the batch record.** Its items record what they can: `batch_incomplete` for installed items whose batch end was not observed (interruption, or UpdateLens itself in the batch, after which nothing is observed), `update_not_completed` / `update_not_installed` for the others.
- **Skipped items are rows, never omissions.** An item whose observation does not fit (time budget: `capture_time_budget`; memory or a failed capture: `analysis_error`) is stored `failed` with no snapshots and every phase `analysis_ended`. Single-plugin updates keep their rule (no row when BEFORE cannot be taken).
- **No BEFORE site check baselines** are attached to items (their AFTER reads `not_captured`), and the update page gets no follow-up for them: website checks belong to the batch (P3).

**Time budget (`Update\CaptureTimeBudget`).**

- The cap is min(10 s, 25 % of `max_execution_time` as configured when the request started, when set); for example 7.5 s with PHP's default of 30 s. It is absolute, not "time left", because of F13 and because web-server timeouts are invisible to PHP.
- Every observation stage of the update request is measured: BEFORE, IMMEDIATE, and the begin or close writes.
- Before each item, the stages it still needs must fit: 2, or 1 with a handoff, each assumed as long as the longest so far.
- An IMMEDIATE that no longer fits fails that item `capture_time_budget`.
- Single-plugin updates are measured but never limited.
- Bound: UpdateLens adds at most the cap plus one stage, because the first stage cannot be known before it runs.

**Remaining limitations of P2.**

- Internal only. No user sees these observations until P3. Rows written with the switch on read as unfinished single reports (see Boundary).
- On sites with very large Action Scheduler queues, the time budget leaves most or all plugins of a batch unobserved (measured above). A signal-aware budget, like the memory plan, would keep options and WP-Cron and skip Action Scheduler first. It is an open question for P3 (below).
- The first stage of a request cannot be predicted, so the budget can be exceeded by one stage (8 s on the cold heavy run).
- Each item's During update usually shows little: the old code still runs (by design). It records what changed in that plugin's interval, never what the plugin caused.
- A batch interrupted between items leaves its items `batch_incomplete`. A crash inside `close_batch()` itself would leave items `captured` until they go stale (15 minutes), then abandoned by a later admin page. That is never a wrong comparison.

### What belongs to one plugin and what describes the batch

| Observation                              | Belongs to            | Why                                                                                                                                                                         |
| ---------------------------------------- | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| During update of item _i_ (BEFOREᵢ → Sᵢ) | the plugin            | Only that plugin's package was installed in this interval. Old code still runs, so it is usually small or empty. It is still an observation, not proof of cause.            |
| Batch end (S_N → E)                      | the batch             | The one `upgrader_process_complete`: other plugins reacting to the updates, cache clean-up, translation updates (F4).                                                       |
| After update (E → SETTLED)               | the batch             | The first request that loads every updated plugin's new code at once. Their upgrade routines interleave and cannot be separated: not by option name, prefix, hook or group. |
| Net result (B₀ → SETTLED)                | the batch             | Includes all of the above.                                                                                                                                                  |
| Potential Impact findings                | the batch             | The rules read the Net result. Findings name records, never "plugin X".                                                                                                     |
| Website checks                           | the batch             | BEFORE is attached at batch begin and AFTER runs after the whole batch. The ledger moves G → G+2 per request, so the existing overlap rule holds for a batch.               |
| PHP errors (P4)                          | the batch, with phase | A file location may name a plugin's directory; that is where the error happened, not which update caused it.                                                                |

### Lifecycle and states

- **Batch analysis:** `captured` (B₀) → `awaiting_settle` (E, at least one item installed) → `completed` (`follow_up`, `admin_shutdown`, `next_update`, `expired`), or `failed` / `abandoned` / `incompatible` as today.
- **Plugin analysis:** `captured` (BEFOREᵢ) → `awaiting_settle` (Sᵢ) → closed **when the batch closes**: `completed` with the new settle outcome `batch` (its After update and Net result are the batch's), or `failed` (its install failed).
- **Starting item _i+1_ does not complete item _i_.** Item _i_ stays open until the batch ends, because:
  - core may still restore its previous version at shutdown (F5), or after a fatal-error check in automatic runs (F7);
  - whether the batch observation succeeds decides how item _i_'s report reads.

  The rule "another update in the same request abandons that request's analysis" changes to: within a recognized batch, the next item is not "another update". It still applies to anything else in the request (a second batch, or a theme or core update between items).

- **P2 alone** (no batch record yet): items close at batch end as `completed` + `batch`, with After update and Net result unavailable (reason `batch_update`). As built, items stay `captured` (not `awaiting_settle`) between Sᵢ and the batch end, and P2 is kept behind an internal switch: see [P2 status](#p2-status-implemented-internal-only).

### Failures, interruptions, overlap and duplicates

| Case                                                                                            | Handling                                                                                                                                                                                                                                                                                                                         |
| ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Item install returns `WP_Error`                                                                 | Item `failed` with the sanitized code at its `upgrader_install_package_result`; the batch continues.                                                                                                                                                                                                                             |
| `upgrader_pre_download` seen, no install result (download or unpack error)                      | Item `failed` `update_not_installed` at batch end (from the `plugins` list) or at shutdown.                                                                                                                                                                                                                                      |
| Up to date, incompatible, or after a `false` result stops the loop                              | Never started: no item.                                                                                                                                                                                                                                                                                                          |
| Batch interrupted (fatal error, timeout, client abort mid-output)                               | At shutdown, `captured` items → `failed` `update_not_completed`, and items with Sᵢ keep their During update. The batch → `failed` `batch_interrupted` (new code), with After update / Net result unavailable. Nothing is captured at shutdown, because memory may be exhausted.                                                  |
| UpdateLens itself is in the batch                                                               | Its files are replaced mid-request, and later autoloads would mix versions. At its `upgrader_pre_download` the batch observation ends: the batch → `abandoned` `updatelens_updated`, items keep During update. Nothing further is captured in that request.                                                                      |
| Same plugin twice in one batch (`?plugins=a,a`)                                                 | The second begin abandons item _a_ (`another_update_started`): its IMMEDIATE no longer describes the final state.                                                                                                                                                                                                                |
| Duplicate completion (bulk `upgrader_process_complete` plus per-item results; a second handler) | Every transition is compare-and-set on `status`. | Another update runs concurrently (another administrator, a cron run)                            | `UpdateActivity::begin()` already returns `others_running`; at E, `current()` is read as well. The result is stored as `overlap` (`none`, `overlapping`, `unknown`), and the report says another update ran at the same time and its changes may be included. Diffs stay; website checks already turn into `overlapping_update`. |
| Same plugin updated by two requests                                                             | Existing rule: a non-stale `captured` analysis of that plugin makes the second request skip it.                                                                                                                                                                                                                                  |
| Next update while the batch awaits settling                                                     | Existing rule: settled first (`next_update`). It now applies to batch analyses too.                                                                                                                                                                                                                                              |

### P3: the batch record and History

- **Storage:** the batch analysis is a row in the same table (`kind = 'batch'`). It needs every lifecycle column (snapshots, diffs, signal reasons, site check columns, compare-and-set). Items point to it (`batch_id`). A separate table was rejected because it would duplicate all of that.
- **Settling:** page-mode follow-up from the iframe (P1's mechanism) naming the batch ID (strict digits, owner check); otherwise `admin_shutdown`, `next_update` or `expired`.
- **Website checks:** BEFORE is attached at batch begin (`Baselines::for_update()` with the request's ledger record). AFTER starts from the iframe's follow-up response (`completed` + `follow_up`), bound to the batch row.
- **API (additive):**
  - batch reports carry `kind` and `batch` (`id`, plus items with plugin, versions, status and error code);
  - item reports carry `batch_id`;
  - an item report's After update and Net result read "Observed for the whole batch", with a link;
  - an item's Potential Impact is Not assessed with a batch category pointing to the batch's findings, never "no findings".
- **History (D5):**
  - One entry per batch: its plugins with their versions and each item's status, plus the batch's configuration and website-check states.
  - Each plugin's details (its During update and status) are reachable from the entry.
  - The menu count counts History entries, so a three-plugin batch is one new report.
  - Single-plugin analyses stay one entry each.

## 2. Automatic updates (P5)

### Recognizing automatic updates

The signal is WordPress's automatic updater itself, not the process that runs it:

- `pre_auto_update` (`type = plugin`, `$item->plugin`) marks that plugin as automatic for this request.
- `UpdateClassifier` accepts a non-bulk `Plugin_Upgrader` download of exactly that plugin when it is marked, on a single site, for any plugin but UpdateLens.
- Without the marker, cron and other non-interactive updates stay ignored.
- The run's analyzed plugin updates form one batch (`update_trigger = automatic`, user 0).

This recognizes the same runs whether WP-Cron is spawned by a visitor, by a system cron calling `wp-cron.php`, or by `wp cron event run` under WP-CLI (F11). Direct `wp plugin update` never fires `pre_auto_update` (F11), so it stays unrecognized and out of scope. The WP-CLI case is not excluded wholesale. Its technical limitations are documented and tested instead:

| Limitation                                                                              | Effect and handling                                                                                                                                                                                                                                                                                 |
| --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One CLI process may run several due events and stay alive for minutes.                  | The finalizer is never settled in the update's own process: the request-start rule (start strictly after IMMEDIATE) rejects it, and since WP-CLI selects due events once before running them (F11), an event scheduled during the run is not run by that process anyway. The next cron run settles. |
| CLI memory is often unlimited (`memory_limit = -1`).                                    | `MemoryBudget` already uses `WP_MAX_MEMORY_LIMIT` or 256 MiB then (existing rule); nothing new.                                                                                                                                                                                                     |
| `max_execution_time` is 0 in CLI.                                                       | `CaptureTimeBudget` uses its fixed ceiling (P2).                                                                                                                                                                                                                                                    |
| No HTTP request: no `$_SERVER` request data, no browser.                                | Nothing in this path reads them; site checks do not apply to automatic updates anyway.                                                                                                                                                                                                              |
| Hosts' own "managed updates" usually call `wp plugin update` directly.                  | Not recognized (no `pre_auto_update`); documented as out of scope.                                                                                                                                                                                                                                  |
| Code that fires `pre_auto_update` itself for something that is not an automatic update. | Theoretically possible; the marker is accepted only for a `Plugin_Upgrader` download of exactly that plugin in the same request. Documented, not defended further.                                                                                                                                  |

Real-site acceptance for P5 runs both a visitor-spawned WP-Cron run and `wp cron event run wp_maybe_auto_update`.

### Capture points

| Point              | Hook                                                                                                         | Notes                                                                                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Item _i_ BEFORE    | `upgrader_pre_download`                                                                                      | First item: batch begin. Earlier awaiting analyses are settled first.                                                                                             |
| Item _i_ IMMEDIATE | `upgrader_process_complete` for item _i_                                                                     | Fires per plugin (F6).                                                                                                                                            |
| Between items      | —                                                                                                            | **No snapshot reuse.** Core toggles maintenance mode, and on 6.6+ runs a loopback with the new code and may roll back (F7). Changes there belong to the batch.    |
| Batch end E        | first `pre_auto_update` for a non-plugin type, else `automatic_updates_complete`, else shutdown              | Themes, core and translations update later in the same run. If a theme or core update followed, the batch report says its After update may include their changes. |
| Item results       | `automatic_updates_complete` (fallback: shutdown, comparing the header version on disk with `version_after`) | A rollback or other `WP_Error` closes the item as `failed` with the whitelisted code, even though `upgrader_process_complete` said success.                       |

WordPress's own check (6.6+, active plugins only) becomes a stored fact per item (`wp_fatal_check`): `no_fatal_detected`, `fatal_detected_restored`, `fatal_detected_restore_failed`, or `not_run` (inactive plugin, WordPress < 6.6, or result unknown). The report states it as WordPress's result, not UpdateLens's.

### Scheduled completion (D2) and the 15-minute window (D3)

1. **Finalizer:** at batch end, schedule one single WP-Cron event `updatelens_settle_automatic` at `E + AUTOMATIC_SETTLE_DELAY` (proposed 60 s). It uses WordPress's own cron spawning; UpdateLens sends no request.
2. **Eligibility:** the cron callback is a new settle path (`SettleEligibility` context `automatic`).
   - It runs only from this hook and only for automatic batches, so manual analyses keep their owner-bound rules.
   - The request-start rule is unchanged: the cron request must have started after E.
   - It runs the new plugin code (`plugins_loaded`, `init`), but not `admin_init`.
3. **Window:** `settle_deadline = E + 900 s` (`AUTOMATIC_SETTLE_WINDOW_SECONDS`) for automatic batches; manual updates keep 300 s. The API's `observation_window_seconds` becomes per analysis (additive; older rows read 300).
4. **Retries:** a capture that fails or does not fit reschedules the event at `+ AUTOMATIC_RETRY_SECONDS` (proposed 120 s) while the window is open, at most `AUTOMATIC_MAX_ATTEMPTS` (3) times. `wp_next_scheduled()` prevents duplicates.
5. **Earlier completion** still happens through existing paths: an eligible admin page (`admin_shutdown`) or the next update (`next_update`).
6. **Stale-analysis recovery:**
   - The cron callback also abandons stale `captured` analyses and expires overdue ones, with the same rules as admin page requests.
   - Report reads keep expiring overdue analyses (`expire_overdue()`, exists).
   - If WP-Cron never runs again, the next admin page or report read expires the batch, which then reads "Partial report".

**Recording coverage and delay explicitly** (provisional columns; see Persistence):

- `settled_captured_at` (`decimal(16,6)`): when the settled snapshot was taken. Coverage = `settled_captured_at − immediate_captured_at`, in seconds.
- `finalizer_ran_at` (`decimal(16,6)`) and `finalizer_attempts` (`tinyint`): when the scheduled finalizer last ran for this analysis and how often, whatever it did.
- The API derives, per analysis, an `observation` object:
  - `window_seconds`;
  - `planned_delay_seconds` (automatic only);
  - `covered_seconds` (null when nothing was settled);
  - `completed_by` (the settle outcome, with `scheduled` added for the finalizer);
  - `finalizer` (`ran_at`, `attempts`, `late_seconds` = `ran_at − settle_deadline` when positive, else null).
- PHP derives the facts; React only words them, e.g. "Observed 9 minutes after the update (planned: about 1 minute)".

**When the finalizer runs late:**

| Situation                                                                  | Result                                                                                                                                                                                                                                                                                                                                                                                  |
| -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Runs after its planned delay but within the 15-minute window               | Settles normally (`completed_by: scheduled`). The report shows the actual coverage; the longer the delay, the more other site activity the After update may contain.                                                                                                                                                                                                                    |
| Runs after the deadline, analysis still `awaiting_settle`                  | **No late snapshot.** It completes the analysis as `expired` ("Partial report"), records `finalizer_ran_at` and the lateness (`late_seconds`), and says so: "The scheduled observation ran 37 minutes after the update, after its 15-minute window, so no After update observation was taken." After update and Net result stay unavailable; never a settled state collected that late. |
| An admin page or report read expired it first                              | The finalizer finds it final (compare-and-set) and changes nothing. The report shows "expired" with no finalizer run recorded before the deadline.                                                                                                                                                                                                                                      |
| Never runs (WP-Cron disabled without a system cron, or the event was lost) | Expired by the next admin page or report read, as above, with no finalizer run recorded.                                                                                                                                                                                                                                                                                                |

**Wording:** "After update was observed in a background request after the automatic update. Routines that run only on admin screens may not have run yet."

Website checks need an administrator's browser and login session, so they do not apply to automatic updates (`site_checks` reason `automatic_update`); the tab says website checks run only for updates started in a browser. History shows "Automatic update". WordPress's own auto-update emails are untouched, and UpdateLens adds none.

### Observer and watch window

- **Observer:** registered once when `updatelens.php` loads on a single site. Each request costs one `error_get_last()` call, and it returns at once unless the error is a fatal type. So a request without a fatal error does no database work; a test asserts zero queries.
- **Watch window:** a non-autoloaded option `updatelens_php_error_watch` (`until`). It is set when an analysis or batch begins and extended to its settle deadline, and read only after a fatal error. Outside a window, nothing is written.

### Ledger: deduplication, overflow, concurrency, retention

The ledger is a non-autoloaded option `updatelens_php_errors` (`Storage\PhpErrorLedgerCodec`, versioned JSON, at most 8 KB). It holds **aggregated groups, not individual events**.

- **Deduplication:**
  - A group key is (`kind`, `source`, `slug`, `request`, `signature`). `signature` is a keyed fingerprint (`Snapshot\KeyedHasher`, new label `updatelens:php-error:v1`) of the error's file path relative to `ABSPATH`, line and message with digits normalized.
  - The fingerprint tells distinct errors apart and merges repeats of the same one. Like every fingerprint, it is internal: never in the API, reports or analysis rows, and only comparable within one site and one set of salts.
  - Each group holds `count`, `first_at` and `last_at` (microseconds).
- **Overflow:** at most `MAX_GROUPS` (20) groups and `MAX_WRITES_PER_WINDOW` (200) writes per watch window.
  - A new group beyond 20 only increments `dropped_groups`.
  - After 200 writes, one last write sets `saturated = true` and nothing more is written until the window ends. A site that fails on every request therefore costs at most 200 small writes, not one per request.
  - Counts are capped at 65,535.
- **Concurrency:**
  - Every change is a compare-and-set on the exact bytes (like `UpdateActivity`), retried at most twice.
  - A write that still loses is dropped, not forced.
  - Counts are therefore **lower bounds**, and the API says so (`counts_are_minimum: true` whenever saturated, groups were dropped, or a write could not be stored; the observer increments `lost_writes` on its next successful write).
- **Retention:**
  - Groups whose `last_at` is older than the start of every open window are pruned on the next write.
  - When no window is open, the ledger is deleted on the next analysis start.
  - What a report keeps is copied into its analysis (below) and lives as long as the history. `uninstall.php` removes both options.

### Attaching to analyses, and the evidence that survives sanitization

- **Copy:** when an analysis or batch closes (settled, expired, failed), the groups with any occurrence inside its interval (BEFORE → end of observation) are copied into `php_errors` (`Storage\PhpErrorsCodec`, at most 4 KB, signatures removed). They are split by phase: before IMMEDIATE is During update, after it is After update.
  - `php_errors_reason` records `not_captured` (older rows or sites that never observed), `observer_unavailable`, or `incomplete` (saturated, dropped groups or lost writes inside the interval).
  - Overlapping analyses get the same groups; batches report them at batch level.
- **What stays:**
  - the error kind (`fatal`, `parse`, `compile`, `user`, `recoverable`, `memory_exhausted`, `timeout`);
  - where the failing file is (`source`: `plugin`, `mu_plugin`, `theme`, `core`, `other`, plus the plugin or theme directory `slug` when the file is inside `WP_PLUGIN_DIR` or a theme root);
  - the kind of request (`front`, `admin`, `ajax`, `rest`, `cron`, `wp_check` for core's scrape loopback, `other`);
  - first and last time, count (a minimum), and how many distinct errors share that place.

  That is enough to say when it happened, in which plugin's or theme's files, for which kind of visitor, and how often. An administrator can then open the PHP error log at exactly that time and see the message and file there.

- **What never stays:** message, file path, line, stack, URL, query string, user, IP. Memory-exhaustion and timeout messages are recognized by fixed prefixes, then discarded.
- **Missing events are never proof of no errors.** The report never says "no PHP errors". The wording is:
  - with nothing recorded: "UpdateLens recorded no PHP fatal errors in the requests it could observe";
  - while incomplete: "At least n…".

  It always offers the blind spots behind a disclosure: errors before UpdateLens loads (F9), requests that never reach WordPress, warnings and notices, sites where observation was unavailable. `not_captured` and `observer_unavailable` read as "Not assessed", never as "nothing found".

### Priority conditions (D4)

A fatal error after an update is an observation in time. It does not prove that the update caused it, and the file's location does not prove which plugin is responsible: plugin X's file can fail because WordPress, a theme or another plugin changed. Priorities are therefore tied to what the administrator can act on, not to blame:

| Priority          | Conditions (all must hold)                                                                                                                                                                                                                                                                                                                                                                                                                   | Next step offered                                                                                                                                         |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **High priority** | 1. Recorded in **After update** (the new code was running).<br>2. In a `front` or `admin` page request (a visitor or administrator got an error page), not only cron, Ajax or REST.<br>3. `kind` is `fatal`, `parse` or `compile`, not `memory_exhausted` or `timeout`, whose location says little.<br>4. The file is inside the directory of **a plugin this analysis updated** (`source = plugin`, slug = an analyzed plugin's directory). | "Open a page as a visitor / an administrator now to see whether it still fails; check the PHP error log at <time> for the message in <plugin directory>." |
| **Needs review**  | Any other recorded fatal error inside the interval: During update; cron, Ajax or REST only; memory or timeout; a file of another plugin, a theme, a must-use plugin, core or elsewhere.                                                                                                                                                                                                                                                      | "Check the PHP error log at <time>; the error happened in <place> during <kind of request>."                                                              |
| Not assessed      | `not_captured`, `observer_unavailable`.                                                                                                                                                                                                                                                                                                                                                                                                      | —                                                                                                                                                         |

The finding text (rule `php_fatal_error_observed`) always has three parts, for example:

- **Observed:** "A PHP fatal error was recorded 3 times in front-end page requests after the update, first at 14:02. The failing code was in files of the plugin directory `example-plugin`."
- **Why it may matter:** "A fatal error stops that request; whoever made it may have seen an error page. Where the error happened does not show what caused it."
- **What to check next:** "Open the site as a visitor to see whether it still fails, and look in the PHP error log around 14:02 for the message and file."

Never "caused by", "broke" or "the plugin crashed".

This changes the `CLAUDE.md` rule "only site check rules may be high priority" in P4. History's `high_priority` count then includes this rule, computed from the small `php_errors` column without decoding diffs.

## 4. Website checks (P6): login page only (D7)

All existing restrictions stay: the check list is fixed and owned by PHP, each target URL comes from PHP, checks are same-origin and comparison stays conservative. The opt-in stays one setting.

| Check          | Target                                                             | Detects                                                                                                                              | Legitimate differences that must not alarm                                                                                                                                                                                                                                                                                                                                                      |
| -------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Login page** | anonymous `GET wp_login_url()` (filtered URLs too, if same-origin) | Fatal or truncated output on the login screen; a redirect that appears after the update. A broken login can lock administrators out. | Hidden-login plugins (404 or redirect both before and after → `failing_both` / `redirected_both`, no finding); HTTP auth on `wp-login.php` (unverified 401 → inconclusive); CAPTCHA or challenge pages (no marker → inconclusive); a login URL that changes between BEFORE and AFTER → `target_changed`, not compared; a login URL on another origin → `not_applicable`, like the other checks. |

- **Markers:** the header on `login_init`, the end marker in `login_footer` (F10).
- **Requests:** a GET only, with `credentials: 'omit'`, so no cookie is kept and no login is attempted.
- **Considered and not added now:**
  - a recent public post (deferred);
  - a wp-admin screen: its `admin_init` would consume plugins' one-time post-update redirects and run upgrade routines, and it would be an eligible settle request;
  - an admin-ajax ping: reports use admin-ajax, so its failure would block its own report;
  - feeds, sitemaps, the anonymous REST index, `wp-cron.php`.

Work:

- `CheckDefinition`, plus `FrontendMarker` hooks and `ResponseClassifier` cases for the target.
- `ReportValidator` IDs, `Baselines` per check, and session limits (more requests per start; the 12-starts rate limit is unchanged).
- Readiness texts: replace the per-combination texts ("homepage only", "REST API only") with a count ("2 of 3 checks ready").
- Schema columns, Website checks rows, and History outcome counts.
- Potential Impact: the site check rules are generic per check, so a newly failing login check is a High priority finding, like the homepage.

## Open questions to confirm when their phase starts

These do not block P3's start.

- **P3:** does History's batch entry show each plugin's During update result inline, or only its status with a link? Both satisfy D5; it is a presentation choice.
- **P3:** on sites with very large Action Scheduler queues one full observation takes 3–8 s (measured in P2), so the 10 s / 25 % budget observes at most one plugin of a batch. Options: keep the budget per stage (simple, observes little there); make it signal-aware, like the memory plan, so that options and WP-Cron (about 0.1 s together) still run and Action Scheduler is skipped first (`snapshot_unavailable` for that signal); or raise the ceiling (more risk of web-server timeouts during an update with maintenance mode on). The recommendation is signal-aware.
- **P5:** the finalizer delay (60 s) and retry interval (120 s) are proposals, to be checked against how quickly WP-Cron actually spawns on low-traffic test sites.
